# Corpus x86 two-entry static export preparation

Preparation only. As of author freeze, Root and independent code review are pending. Their separate reports carry the later disposition. No Ghidra, Java/compiler, decoder, original slice import or guest execution has run here. Only the analyst-owned synthetic Mach-O data builder and read-only offline scope checks ran.

This version derives [CorpusX86SelectedExport.java](CorpusX86SelectedExport.java) from the immutable selected-entry exporter and [run-selected.py](run-selected.py) from the immutable targeted driver. It has exactly two unique ordered entries, `0x23b0` and `0x29c0`, each with a 1,024-byte window. It cannot add a third entry, grow a window, export callees or run whole-program analysis. Existing body ambiguity, boundary, overlap, partial-instruction and control-flow guards remain byte-identical. A failed entry or partial C output is retained; process exit zero alone is insufficient.

The proposed import supplies the complete thin Program as data. The decompiler can read global data, signatures and other program metadata outside the two windows. The bound describes function construction, listing and output scope; it is not a byte-read sandbox. No guest code is invoked or emulated.

The Java script explicitly disables headless analysis and strictly checks Ghidra 12.1.4, language `x86:LE:64:default`, compiler `gcc`, base zero, JDK 21.0.12.1, a 4 GiB heap and CPU/pool two. The expected language/compiler is a nomination from retained main-Live x86 metadata, not Corpus proof: a differing fixture or Corpus import must fail. The launcher also uses `-noanalysis -readOnly -deleteProject` with a fresh private transient project, home, temporary and cache directories. No existing ARM project is opened.

The resource policy reuses the existing driver's owned process-group monitor: 4 GiB **heap**, 6 GiB aggregate group RSS, 3 GiB free-disk floor, CPU two, 180-second supervised tool deadline and 60 seconds per decompile. One-second sampling, bounded `ps` calls and separate cleanup mean these are supervisory bounds, not exact timing guarantees. PID/start strings anchor group cleanup; escaped descendants or unprovable identity are not silently treated as closed. No retry occurs. Root's outer coordinator must independently retain pretry, interruption and catastrophic-I/O outcomes.

The two input configs differ only in `source` and `target_sha256`. [synthetic-corpus-x86.macho](synthetic-corpus-x86.macho) is entirely analyst-owned: at `0x23b0` it contains `MOV EAX,42; RET`, and at `0x29c0`, `XOR EAX,EAX; RET`. It is data, never a native executable test. The intended fixture positives are two complete functions with known 6-byte/3-byte bodies and two instructions each; actual compilation/decompilation remains untested.

Root must separately select the fixture launch after full code preflight. Its two successful exports and independent actual review are prerequisites for any separate actual-mode selection. The driver checks pinned fixture artifacts, successful status, cleanup and a Root-selected independent-review identity before reading/extracting the original x86 slice. The original target is the exact 250,352-byte slice at universal offset 16,384, SHA-256 `03be50fae8abee39dcaafec743d82ab4c908d548977354528aa1b8dd3919b00d`. No original slice was extracted in this preparation.
