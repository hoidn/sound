# Live Set structure (T1.1)

Workstream T1.1 of [roadmap revision 3](native-decompilation-roadmap.md#revision-3--t1-completion-plan-2026-10-18),
for target T1 ([ADR 0004](../decisions/adr-0004-target-scope-t1.md)). Question: what document
structure must a Live Set have, below the envelope that
[SPEC-ALS-CONTAINER](../specs/als-container.md) covers, for the T1 content to be read: tracks,
mixers, clip slots and scenes, clips, sample references, device chains of the seven bundled
devices, sends and returns, automation targets, and the Id rules? Which documents does the
reader refuse, and which does it repair? Everything here is static (the shipped schema, the
shipped documents and the reader code), except one extracted-execution run of the sample CRC
(label X). No document was opened by Live. The spec built from this page is
[SPEC-LIVE-SET-STRUCTURE](../specs/live-set-structure.md).

The generic reader (member lookup by name, missing members, duplicates, unknown elements,
value text) comes from [transport-state native](transport-state-native.md#how-a-set-reaches-the-transport-objects),
and the envelope from [document container native](document-container-native.md). They are
not repeated here.

**Answer (draft).** The schema file predicts every element of a shipped `12.0_12402` document
(375 of 375), so it serves as a conformance test for a written set. On top of the generic reader,
the set-level code that runs whenever a set is opened (settled by a follow-up trace of the open
path, [below](#open-path-and-the-post-load-checks)) refuses a set with no audio, MIDI or group track, a player track
after a return track, a track whose freeze-sequencer slot count differs from its session slot
count, a mixer with more send holders than return tracks, a present pointee with Id 0,
`NextPointeeId` not above the largest pointee Id, and a duplicate list-item Id. It repairs
missing send holders, removes envelopes whose target is missing, gives absent pointees new
Ids, and asks before renumbering duplicate pointee Ids. A sample is found by a typed relative
path first and, for some types, by its absolute path; a missing file does not stop the set
opening. The sample identity CRC was run as original x86_64 code (X). No load check compares
session slots with scenes or `SendsPre` with returns. Of the released fixtures, 204 are refused
by these checks although 178 cases expect them to open, in six releases of five families (see [released fixtures](#released-fixtures-against-the-shipped-structure)).

## The schema describes the document

The schema file is itself a class list. Each class element lists its fields with `Class` and
`Type`. Read with the four forms below, it predicts every element of every shipped
`12.0_12402` document. `schema_check.py` walks each document from `LiveSet` down and reports any
element or attribute that its parent's class does not declare, and any child out of the class's
field order.

| Type | Form in the document |
| --- | --- |
| `0` | A compound child element of class `Class` |
| `-4` | A base value, either an attribute of the parent (`<MidiTrack Id="1" SelectedToolPanel="7">`, `<MidiClip Time="0">`) or a child element with one `Value` attribute (`<LomId Value="0" />`). The schema does not say which; the reader's member flag does ([N1](transport-state-native.md#names-order-and-attributes-come-from-the-member-registry)) |
| `-1` | A list or slot (`RemoteableList`, `Slot<…>`): its children are elements named by their own class, each list item with an `Id` attribute (`<Tracks><MidiTrack Id="12">`, `<ClipSlot><Value><MidiClip Id="0" …>`) |
| `-3` | An array whose items are named by `ArrayTranslator` (`KeyTrack/Notes/MidiNoteEvent`) |

**Observed** (`out/schema-check-{als,alc}.jsonl`): in all 375 `12.0_12402` documents (25 sets,
350 clip files) every element is a declared field of its parent's class, every list item is a
schema class, and children occur in the class's field order. The only deviations are two base
values with several attributes (`LiveSet/VideoWindowRect` with `Top`, `Left`, `Bottom`,
`Right`; `AbletonDefaultPresetRef/DeviceId`). The one `12.0_12117` set (the default template)
also holds `NeedArrangerRefreeze`, `ClipSlot/NeedRefreeze` and `SpanAlgorithm/FixedLength`,
which `12.0_12402` no longer declares, and two `MidiClip` children out of the newer order.

**Inferred:** the schema is the program's member registry written out (the N1 and S5 packets
found registry order equal to schema order for `Transport`, `AClip`, `AFollowAction` and
`ASong`). The checker is therefore a usable conformance test for a written set, with one gap:
whether a `-4` member is an attribute or an element must be taken from shipped documents.

## Document skeleton

`LiveSet` (schema class `LiveSet`, `InternalName="LiveDocument"`) declares 89 fields. Shipped
`12.0_12402` sets store 75 of them, in schema order, in all 25 sets (one, `SelectedBreakpointValue`,
is missing from the 12117 template). The T1 fields among them, in order:

| Field | Class (Type) | Shipped form |
| --- | --- | --- |
| `NextPointeeId` | Int (−4) | `<NextPointeeId Value="22182" />`, first child |
| `Tracks` | RemoteableList (−1) | `AudioTrack`, `MidiTrack`, `GroupTrack`, `ReturnTrack` items |
| `MainTrack` | MainTrack (0) | One element, no `Id` |
| `PreHearTrack` | PreHearTrack (0) | One element, no `Id`; the cue/preview track |

| `Scenes` | RemoteableList (−1) | `Scene` items |
| `Transport` | Transport (0) | [SPEC-TRANSPORT-STATE](../specs/transport-state.md) |

| `CrossfadeCurve` | RemoteableEnum (0) | [SPEC-MIXER-VALUES](../specs/mixer-values.md) REQ-009 |

The other stored `LiveSet` fields are view state, grids, scale, locators, groove pool,
tuning and note algorithms; T1 does not use them.

## Tracks

**Observed** over the 26 sets (`out/documents.json`, `.als`):

- **Types and counts.** 124 MIDI, 91 audio, 20 return and 3 group tracks. Every set has
  exactly one `MainTrack` and one `PreHearTrack` outside `Tracks`. The 350 clip files hold one
  MIDI track each.
- **Order.** In every set, every `ReturnTrack` follows every other track in `Tracks`
  (26 of 26). Audio, MIDI and group tracks are interleaved freely.
- **Track Ids.** Every item of `Tracks` has an `Id`, unique within the list (26 of 26). The
  values are arbitrary small integers, not positions (for example `12 13 8 14 2 3` in the default
  template). In 39 of 238 tracks the value equals some pointee Id of the same set, so track Ids
  and pointee Ids are separate spaces. `MainTrack` and `PreHearTrack` carry no `Id`.
- **Attributes.** Every track element carries `Id`, `SelectedToolPanel`,
  `SelectedTransformationName` and `SelectedGeneratorName` (view state, base values written as
  attributes); `MainTrack` and `PreHearTrack` carry the last three.
- **Names.** `Name` holds `EffectiveName`, `UserName`, `Annotation` and `MemorizedFirstClipName`.
  `UserName` is empty in 80 of 238 tracks, with `EffectiveName` holding a generated text such as
  `1-MIDI`. 22 tracks have a `UserName` that differs from `EffectiveName`. The main track is
  `EffectiveName` `Main` with an empty `UserName` in 26 of 26; the cue track `Master` or `0-Main`.
- **Colours.** `Color/@Value` is an integer: 0 to 69 on audio, MIDI, group, return and main
  tracks, −1 on every cue track.
- **Group membership.** `TrackGroupId` is −1 except on 13 audio tracks inside a group track.
  Group tracks are outside T1.
- **Routing.** `DeviceChain/AudioOutputRouting/Target` is `AudioOut/Main` for every MIDI and
  return track, 77 of 91 audio tracks and the 3 group tracks; 13 audio tracks route to
  `AudioOut/GroupTrack` and one to an external output. The main and cue tracks route to
  `AudioOut/External/S0`-form outputs. The routing values and their display strings are view and
  hardware state outside T1, except that a T1 track outputs to the main track.

**Chain layout per type** (schema and 26 of 26 sets; `DeviceChain` children):

| Track | `DeviceChain` children | Inner chain class |
| --- | --- | --- |
| `MidiTrack` | `AutomationLanes`, `ClipEnvelopeChooserViewState`, four routings, `Mixer`, `MainSequencer` (MidiSequencer), `FreezeSequencer`, `DeviceChain` | `MidiToAudioDeviceChain` |
| `AudioTrack` | the same, `MainSequencer` of class AudioSequencer | `AudioToAudioDeviceChain` |
| `ReturnTrack` | four routings, `Mixer`, `DeviceChain`, `FreezeSequencer`; no `MainSequencer` | `AudioToAudioDeviceChain` |
| `MainTrack` | four routings, `Mixer` (MainTrackDevice), `FreezeSequencer`, `DeviceChain` | `AudioToAudioDeviceChain` |
| `PreHearTrack` | four routings, `Mixer`, `DeviceChain` | — |

**Reader rules** (`traces/tracks/trace.txt`; x86_64 `0x1027b1a00` disassembly read):

- The set's validation step (ASong slot +0x100, run by the post-order walk) takes the `Tracks`
  list. A *player* track is an audio or MIDI track or a group track. An empty list, or one with
  no player track, is refused with "Set has no player tracks". A player track after a non-player
  (return) track is refused with "Return tracks out of order". A track whose `TrackGroupId` is not
  −1 must lie under its open group ("Track grouping corrupt"), and a group must have members
  ("Empty track group"). All are corrupt-document errors.
- The set constructor creates the cue track, the main track and empty `SendsPre`, `Scenes` and
  `Tracks` lists. A document without `MainTrack` or `PreHearTrack` therefore keeps the
  constructed track; one without `Tracks` is refused by the rule above.
- No check of track Id uniqueness was found in the track code; the generic list loader refuses
  duplicate list-item Ids (below), which covers `Tracks` if it is read by that loader.
- Not established: what any other class in `Tracks` does, and the routing a track gets when
  `AudioOutputRouting` is absent.

## Mixers

[SPEC-MIXER-VALUES](../specs/mixer-values.md) REQ-001 places the mixer at
`<Track>/DeviceChain/Mixer` for all six track types and gives its value fields. This survey
re-measured only the send-holder counts: every audio, MIDI, group and return mixer holds one
`TrackSendHolder` per return track, and the main and cue mixers hold none (26 of 26 sets).
Holder `Id`s equal the `SendsPre` item `Id`s in 235 of 238 tracks; three MIDI tracks of
`Quick Start Song.als` have holders `0 1` against `SendsPre` `0 2`. So holder and `SendsPre`
Ids are not a reliable link; position is.

## Clip slots and scenes

**Observed** (`.als`):

- **Counts.** Every audio and MIDI track's `MainSequencer/ClipSlotList` holds exactly one
  `ClipSlot` per `Scene` (215 of 215 tracks); every group track's `Slots` list one
  `GroupTrackSlot` per scene (3 of 3). Scene counts range from 1 to 511 (706 scenes). Return,
  main and cue tracks have no session slots.
- **Slot Ids.** 176 of 215 tracks number their slots `0 … n−1`. The other 39 reuse the scene
  Ids in scene order (for example `16 9 10 25 26 11 12 21` in `Live 11 Intro Empty.als`), and
  one set mixes the two forms between tracks. Slot Ids therefore do not name a scene;
  position does (inferred).
- **Slot form.** `<ClipSlot Id="…"><LomId Value="0" /><ClipSlot><Value>…</Value></ClipSlot><HasStop Value="true" /></ClipSlot>`.
  The inner `ClipSlot` is a `RemoteableSlot` whose `Value` holds zero or one clip. 3,385 of
  7,498 slots hold a clip (2,845 `AudioClip`, 540 `MidiClip`), the rest an empty `<Value />`.
  `HasStop` is `true` in every shipped slot. The clip element carries `Id` and `Time`
  attributes; `Id` is `0` in 2,919 of 3,385 and `Time` is `0` in all.
- **Scenes.** Every `Scene` has an `Id` and the children `FollowAction`, `Name`, `Annotation`,
  `Color`, `Tempo`, `IsTempoEnabled`, `TimeSignatureId`, `IsTimeSignatureEnabled`, `LomId`,
  `ClipSlotsListWrapper` (706 of 706). Scene Ids are `0 … n−1` in 15 of 26 sets and arbitrary
  in the others. `Name` is empty in 586. `Tempo` is `120` with `IsTempoEnabled` false in 697;
  9 scenes enable a tempo (74 to 160). `TimeSignatureId` is `201` (4/4) except one `302` (6/8),
  enabled in 9. `Color` is −1 in 697 and 69 in 9.

**Reader rules** (`traces/tracks/trace.txt`; x86_64 `0x1026f1720` disassembly read):

- The player-track validation step compares the slot count of the track's session sequencer
  with that of its freeze sequencer and refuses a mismatch with "Slot count mismatch.". It does
  not compare either with the scene count.
- The MIDI and audio track chain constructors create both sequencers, and the sequencer base
  creates its slot list empty, and nothing adds freeze slots while the set is read (settled by the
  follow-up trace, [below](#open-path-and-the-post-load-checks)). So a track with session slots and
  no `FreezeSequencer` element is refused.
- No load path compares the session slot count with the scene count. The only code that reads
  both is the player track's per-scene freeze loop, which does not resize. A set with more or
  fewer slots than scenes, or with slots and no scenes, has no established outcome.
- The `clipSlots(track).size() == slotCount` assertion belongs to the Push model code, not the
  document reader.

## Sample references

**Observed** (`.als`; the clip files hold no audio clip). Every one of the 2,845 session
`AudioClip`s holds a `SampleRef` with the children `FileRef`, `LastModDate`, `SourceContext`,
`SampleUsageHint`, `DefaultDuration`, `DefaultSampleRate`, `SamplesToAutoWarp`, and a `FileRef`
with `RelativePathType`, `RelativePath`, `Path`, `Type`, `LivePackName`, `LivePackId`,
`OriginalFileSize`, `OriginalCrc`, `SourceHint`, all as `Value` elements. All 2,845 have
`RelativePathType` 5, `Type` 2, a `RelativePath` under `Samples/` (`One Shots` 2,476, `Loops`
367, `Multisamples` 2), an absolute `Path` on the authoring machine (`/Volumes/data/tmp/…`), a
non-empty `LivePackName`, and an empty `SourceHint`. Files are `.wav` (1,904) or `.aif` (941).
`OriginalFileSize` is nonzero in all and `OriginalCrc` in all but one. `DefaultSampleRate` is
44,100 (2,363), 96,000 (289), 48,000 (190), 22,050 (1) or 22,000 (2).
`DefaultDuration` and `LastModDate` are nonzero in all. The shipped sets therefore show only
one reference form, a pack-library reference.

**Reader and writer** (`traces/fileref/trace.txt`; x86_64 `0x1014d8e20` and `0x1014d99d0` branches read):

- **Codes.** `RelativePathType`: 0 Unknown, 1 Document, 2 Library, 3 Project, 4 IdBased,
  5 Live Pack (named by `LivePackName`), 6 UserLibrary, 7 Builtin. `Type` is always set to 2 by
  the save-side update and is 2 in all 10,440 shipped sample references; its meaning was not
  traced. A new `FileRef` starts with every number 0 and every string empty; the class itself
  does no resolution.
- **Identity.** `OriginalFileSize` is the file size. `OriginalCrc` is CRC-16 (polynomial 0x8005,
  MSB first, initial 0, no reflection, no final xor; the CRC-16/UMTS parameters) of the first
  min(size, 16,384) bytes. `crc_check.py` matches 2,984 of 2,984 bundle files referenced by
  shipped documents. **X:** the x86_64 step function `0x101191310` (arm64 `0x1011b6e88`; caller
  `0x10125a540` / arm64 `0x101279eac`) returned the rule's value for all 8 inputs, among them
  47,018 for the T11-MIN sample's first 16,384 bytes and 0xFEE8 for `123456789` (`out/x-crc.json`).
  The loader takes at most 4,096 bytes per buffer, so longer inputs were fed in pieces with the
  running CRC passed back, as the caller does per block. The function is integer-only, so the
  arm64 slice computes the same value. `DefaultDuration` and `DefaultSampleRate` equal the file's
  frames and integer rate in 2,983 of 2,983 WAV and AIFF references (`duration_check.py`).
  `LastModDate` is the file time in seconds since the epoch, 0 on error.
- **Resolution on open.** The sample reference's post-load step takes as base the folder of the
  document being read and, when a resolution context is on the reader's stack, joins a
  non-empty `RelativePath` to a root chosen by type: 0 and 1 the base, 3 the project root found
  from the base, 5 the root of the pack named by `LivePackId`, 6 the user library, 7 the built-in
  content; 2 has no candidate and 4 gives no path. The first existing candidate wins (types 2, 5
  and 7 also try a library relocation). Otherwise types 0, 1, 2 and 6 fall back to a non-empty
  absolute `Path`, without the size and CRC identity; types 3, 5 and 7 do not use `Path`. No
  traced branch throws, so an unresolved file does not refuse the set; the media manager sets a
  "missing files" status. Who fills that status and what the user sees were not traced.
- **Length and rate.** The stored `DefaultDuration` and `DefaultSampleRate` seed the sample
  object before the file is read (−1 when absent). Whether a file with a different real length
  or rate overrides them was not traced.
- **Formats.** An extension table lists `.aif`/`.aiff`, `.wav`, `.bwf`/`.rf64`, `.flac`, `.mp3`,
  `.ogg`, `.m4a` and others; decoding goes through Apple's AudioToolbox, which is not available
  here. Which formats a clip decodes, by extension or by content, is open.
- **Save.** When the file exists and changed, the update writes the absolute `Path`, `Type` 2,
  and the first `RelativePathType` that applies of 7, 5, 6, 3, 1; 7, 5, 6 and 3 require the file
  inside the root, 1 does not (shipped type-1 paths, all of them preset and source references,
  start with `..`). Otherwise it writes 0 with an empty `RelativePath`, then recomputes size,
  CRC and `LastModDate`. The project-root rule and the same-volume condition for type 1 were
  not read.

## Device chains and the seven devices

**Observed.** A track's devices are the items of `DeviceChain/DeviceChain/Devices`. In the
shipped sets that list holds ordinary native devices directly (for example `Operator` and
`Drift` on MIDI tracks, `Compressor2` and `Reverb` on audio tracks, `Delay` on returns) and
racks. The seven bundled devices (`Amp`, `Cabinet`, `UltraAnalog`, `StringStudio`, `Collision`,
`LoungeLizard`, `Corpus`) occur 36 times in the sets and 577 times in the clip files, and **every
occurrence is inside a rack**: `…/InstrumentGroupDevice/Branches/InstrumentBranch/DeviceChain/MidiToAudioDeviceChain/Devices`
or `…/AudioEffectGroupDevice/Branches/AudioEffectBranch/DeviceChain/AudioToAudioDeviceChain/Devices`.
No shipped document places one directly in a track chain. Each occurrence carries an `Id`
attribute, as a list item.

**Inferred (schema).** A MIDI track's inner chain and a rack branch's chain are the same class,
`MidiToAudioDeviceChain`; an audio, return or main track's inner chain and an effect branch's
chain are both `AudioToAudioDeviceChain`. Both classes declare only `Devices` (a list) and
`SignalModulations`. The element form of a device inside a track chain is therefore the form the
shipped racks show. Whether the reader accepts any device class in any chain position is a
reader question (below).

No reader trace of the device lists' class test was made. The four instruments also ship a
default device preset whose root holds the bare device element
(`Core Library/Defaults/Instruments/Analog.adv`, `Collision.adv`, `Electric.adv`, `Tension.adv`),
the form a device has when inserted on its own; Amp, Cabinet and Corpus have no default preset.
The spec therefore states direct placement as conditional on assumption A6.

## Ids and NextPointeeId

**Observed** over all 376 documents (`out/documents.json`):

- Two Id spaces occur. *List-item Ids* are the `Id` attribute of list items (tracks, scenes,
  clip slots, devices, envelopes, events, KeyTracks, `SendPreBool`, send holders, warp markers):
  unique within their list in every list with more than one item (10,750 in the sets, 16,882 in
  the clip files).
  *Pointee Ids* are the `Id` attribute of `AutomationTarget`, `ModulationTarget`, `Pointee`,
  the eight `…ModulationTarget` elements of an audio sequencer and the 131 `ControllerTargets.N`
  elements of a MIDI track (schema classes `Pointee` and the five target classes): 215,734 in the
  sets, 747,856 with the clip files (`out/schema-check-{als,alc}.jsonl`).
- Pointee Ids are nonzero and unique across the whole document in every set and clip file, and
  `NextPointeeId` is exactly the largest pointee Id plus one in every one of them (376 of 376).
  The smallest pointee Id in a set is 1 to 141.
- `PointeeId` in every track envelope names an `AutomationTarget` (355 of 355 in the sets).

**Reader rules** (`traces/pointee/trace.txt`; x86_64 `0x101525600`, `0x10153df90`,
`0x101533ae0`, `0x101533040` and `0x10145f320` disassembly read):

- **Pointees.** The pointee base registers `Id` as an attribute; the classes sharing its
  post-load step are the device `Pointee`, the Float, Enum and Bool automation targets, the
  timeable automation and modulation targets, the user-float modulation target and two envelope
  target classes. An envelope's `PointeeId` is a separate pointer class with a child element.
- **Id 0.** The pointee post-load step refuses a pointee read with Id 0 ("Invalid Pointee Id.")
  unless a preset-extraction flag is set; the flag is set only around preset and device loading.
- **NextPointeeId.** It is a document member (constructor value 1). The set's root post-load
  step (LSong::AfterRead_Virtual) walks every pointee, takes the largest Id (signed, from 0) and
  refuses the set when `NextPointeeId` is not greater ("NextPointeeId is too low: {} must be
  bigger than {}").
- **Duplicates.** Ids used more than once go to the song's repair: unless a drag is in
  progress, a Yes/No message (`sErrorCorruptDocumentNonUniquePointeeIds`) is shown; on Yes,
  every pointee with a shared Id in a track or the main track is given a new Id from the
  counter, the first occurrence included, same-track references are rewritten, ambiguous ones
  are removed or the repair fails (`sErrorNonUniquePointeeIdsRepairFailed`); then
  `sDialogRepairSuccessfulPleaseSave`. A duplicate that survives to registration aborts the
  application.
- **Registration.** After the checks every pointee is registered; one with Id 0 (constructed,
  not read) gets the counter's value, and the counter is kept above every registered Id.
- **Dangling envelopes.** Next, the song removes every track and clip envelope whose
  `PointeeId` is 0 or not registered ("Purging dangling … envelope with PointeeId"), gated on
  an application flag that its constructor sets to 1. A later step removes "empty" or
  "half-dangling" envelopes under conditions not interpreted. Resolving a dangling pointer that
  survived would abort.
- **List-item Ids.** The attribute handler parses a list item's `Id` with the integer rule and
  refuses a negative or non-integer value ("Illegal value for 'Id' attribute"). The list loader
  refuses an unknown class ("Unknown class … found"), a class the list does not accept
  ("Illegal class of list member"), and a repeated Id ("Non-unique list ids"). An item without
  `Id` is refused when MajorVersion is 5 or more and a reader flag is set; the flag was not
  interpreted. The list writer writes each entry's held Id.
- **Translators** 368 and 369 also handle `NextPointeeId`, for older documents only.

## Open path and the post-load checks

Follow-up trace, both corpora (`traces/a1a2/trace.txt`). It settles the spec's A1 to A3.

- **Every open route reaches one load method.** Opening for the user ("Loading Document For User",
  application slot +0x730), the command line ("Loading command-line document...") and crash
  restore all call the application's load method, slot +0x840. Live's application class has one
  implementation of it. That implementation sends Note sets (`.abl`, `.ablbundle`) to an import
  path, and every other file to the function that logs `Loading document ` and calls the general
  reader. The x86_64 slice has the same chain.
- **The XML reader always runs the checks.** After parsing, the general reader's XML branch calls
  one load step for every document it returns. That step creates the root and loads it. It runs
  the root's post-load step (for a set, LSong::AfterRead_Virtual) when the reading context's flag
  is set, and then always runs the validation walk, which ends in each object's +0x100 check
  (x86_64 disassembly read). The reading context's constructor sets the flag (x86_64
  disassembly), and only the undo-history stream clears it. The version-aware reader returns
  parsed nodes without objects and is not on the open path.
- **Freeze sequencers start empty.** The audio and MIDI track chain constructors create both the
  session and the freeze sequencer. The sequencer base creates an empty slot list. Outside the
  list reader, slots enter a sequencer only through one insertion routine. Its callers insert
  scenes and create tracks, all edit paths, and no load step reaches any of them by direct calls
  (`reach.txt`). The MIDI track's post-load step loops over scenes only for a frozen track, and
  only to update the engine.
- **The preset exemption is off.** The flag that exempts pointee Id 0 is set only by preset,
  device-preset and debug-browser code, none of which the open path calls.
- **Not run.** None of these checks is a self-contained function, so extracted execution was not
  used.

## Minimal T1 set

`make_fixture.py` writes T11-MIN from invented values: one MIDI track (a two-note clip, Analog),
one audio track (a clip on a generated 1 s sine WAV, Amp), one return track, the main and cue
tracks, `SendsPre`, two scenes, transport and quantization. It has both sequencers with one slot
per scene, one send holder per return, 68 pointees with Ids 1 to 68 and `NextPointeeId` 69, a
volume envelope on its target, and a Document-relative sample reference with the real size,
CRC, length, rate and file time. `schema_check.py` finds no deviation, and every structure
measurement is the one the spec requires (`out/schema-check-fixture.jsonl`). Two runs produce
byte-identical files. The spec's REQ-018 lists each element as required, value-bearing,
optional or "write it".

## Limitations

- Static, apart from the CRC step run in the harness. No document was opened by Live, and no

- Shipped documents were written by 12.4d1 and 12.1d1, not by a 12.4.3 save.

  was read (marked in the traces).
