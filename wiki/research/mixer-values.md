# Mixer values: storage, display and gain conversion

Packet S9 (FEAT-AUDIO), from the [scope extension](native-decompilation-roadmap.md#scope-extension--2026-10-17)
of roadmap revision 2. Question: how are a track mixer's volume, pan, send and
crossfade-assign values stored, and how does Live convert stored values to the
displayed units (dB, pan position) and to linear gain? The page has a static half
(schemas and shipped documents) and a native half (constructors, conversion code,
display formatting and the engine-side gain stages). Nothing was executed. Statements
about audio come from code and are static derivations, not measurements; every one
of them has a Phase 4 probe below. The document envelope, loader and number writer are
covered by [document container native](document-container-native.md) and
[transport-state native](transport-state-native.md) and are not repeated.

## Stored value → position → gain: the fader curves

**Observed** (✓ s9-0001 `0x101ac2bf8`, `0x101ac3498`; ✓ s9-0002 `0x101ac3bac`; ✓ s9-0003
`0x101ac3c94`). A registry slot (`0x101ab9e24(10)`) holds seven curve objects, built by
`0x101ac35d8`. Each object has a 101-entry dB table and a 101-entry gain table. Their
names (`0x1067568f8`) and integer ranges (`0x1058486a8`/`0x1058486c4`) match by index:

| Mode | Name | dB range | Table construction (float32) | Used by |
| --- | --- | --- | --- | --- |
| 0 | `-70 to 0 dB` | −70…0 | 60 points from max in −0.4 dB steps, then 37 points whose step grows by 0.04 dB, then a landing on min | track sends |
| 1 | `-70 to +6 dB` | −70…+6 | as mode 0 | track volume; engine volume stage |
| 2 | `-40 to +3 dB` | −40…+3 | constant −0.4 dB step | not traced |
| 3 | `-70 to +24 dB` | −70…+24 | as mode 0 | not traced |
| 4, 5 | `-66 to +6 dB Logarithmic`, `-42 to 0 dB Logarithmic` | | constant step (max − min)/101 | not traced |
| 6 | `-70 to 6 dB RMS` | −70…+6 | −0.6 dB steps, increment 0.015 dB | not traced |

Values with |x| < 1e-4 are set to 0. The last two points before min use a fused
multiply–add correction (`0x101ac30ec`). The gain table is `exp10f(dB·0.05)` in reverse
order, so index i is position i/100. Position → gain (`0x101ac3498`) interpolates
linearly in gain between neighbouring points. Positions ≤ 0 give gain[0] and positions ≥ 1
give gain[100]. Gain → position (`0x101ac353c`/`0x101ac3c94`) is a binary search with the
inverse interpolation, 0 below gain[0] and 1 above gain[100]. Both conversions are the
identity while a global flag (`DAT_106f7e914`) is set. Only scope helpers set it
(`0x101ac3d74`); its runtime use is unknown.

**Derived** (`curves.txt`), track volume (mode 1) and send (mode 0):

| dB | Gain (float32) | Volume position | Send position |
| --- | --- | --- | --- |
| +6 | 1.99526238 | 1.00 | — (clamped to 1.0 gain) |
| 0 | 1 | 0.85 | 1.00 |
| −6 | 0.501187205 | 0.70 | 0.85 |
| −12 | 0.251188636 | 0.55 | 0.70 |
| −18 | 0.125892535 | 0.40 | 0.55 |
| −24 | 0.0630957335 | 0.3024 | 0.40 |
| −48 | 0.00398107152 | 0.1035 | 0.1429 |
| −60 | 0.001 | 0.0346 | 0.0678 |
| −70 | 0.0003162277571 | 0 | 0 |

The mode 1 table above 0.39 is linear in dB (0.4 dB per 0.01). Below that the steps grow
from 0.44 to 1.88 dB, and the last points are −60.92, −63.37, −66.4 and −70 dB.
**Inferred:** the position is the fader and MIDI-mapping domain (`AMidiControllerRange`
uses the same control). This was not traced to the UI.

Arrow-step slots `+0x40`–`+0x58` of the volume control (`0x10255da18` ✓ s9-0004 and three
siblings in pseudocode) move by +1, −1, +0.1 and −0.1 dB through the curve. A gain of
0 counts as −140 dB.

## Display text

**Observed** (✓ `0x102183bf4`, `0x102183abc`, `0x101437334`, `0x101431c6c`; volume and send
share one formatter instance per class, built with `(3, 1, 1, 1)` ✓ `0x10271c138`):

1. dB = `log10f(gain) × 20` in float32, widened to double. A gain ≤ 0 gives −140.
2. If dB ≤ −70 + 0.3, the text is `-inf`.
3. Otherwise the value is printed with `%.*f` at 3 decimals. The rounding test uses
   `frinta`; a value that rounds to 0 prints as 0. Trailing zeros are removed down to 1
   decimal, and |dB| ≥ 100 would print with no decimals. The suffix ` dB` follows.
4. Text → gain (`0x102183c64`, pseudocode): parse a number, then `exp10f(dB·0.05)`.
   Unparsable text gives the invalid marker.

**Derived** (`derive_curves.py`): gain `1` → `0.0 dB`, `0.5011872053` → `-6.0 dB`, `0.2494` →
`-12.062 dB`, `1.99526238` → `6.0 dB`, −69.7 dB → `-69.7 dB`, −69.8 dB and the minimum
`0.0003162277571` → `-inf dB`. A second slot (`0x1014374b4`, pseudocode) formats the same
digits without `-inf` and without the suffix; which UI element uses which slot is not traced.

**Pan** (✓ `0x10143a290`): `C` when −0.01 ≤ p ≤ 0.01; otherwise |p|×50 printed with 0
decimals followed by `L` (p < 0) or `R` (p > 0). So −1 → `50L`, 0.6 → `30R`, 0.0101 → `1R`,
and the shipped `0.004999999888` → `C`. Parsing (`0x10143a3d8`, pseudocode) divides the number
by 50; whether `L`/`R` suffixes are accepted is unknown.

## Engine gain stages

**Observed** in the audio engine:

- **Volume stage and the −∞ floor** (✓ `0x101aede40`, `OCrossFadeVolumeProcessor`): the
  volume input ramp passes through curve mode 1 (position → gain). The crossfade factor is
  applied next (below). A result ≤ 0.00032 (`0x39a7c5ac`) becomes exactly 0. The generic
  `OConvertLevelProcessor::OnIn` (✓ `0x101aee5e8`) applies the same rule for its configured
  curve. **Inferred:** the logic layer sends the volume as a position (the gain → position
  slot), so a stored gain round-trips to the same gain. The stored minimum (−70 dB, display
  `-inf dB`) is rendered as silence, and any stored gain at or below 0.00032 (−69.9 dB) is
  silent too. The value the logic layer puts on the `Volume` port was not traced
  (PRB-S9-01).
- **Pan law** (✓ `0x101b3b95c`): per track, a 2×2 matrix from inputs [w, pan, splitL, splitR,
  vol] (✓ `0x101afb494`; ramps 0–3 are written by `OnPanRampEvent<0…3>`, ramp 4 by
  `OnVolume`). With θx = (x + 1)·π/4:
  - L→L = vol·(w·cos θL + (1 − w)·max(1e-5, √2·cos θpan))
  - L→R = vol·w·sin θL
  - R→L = vol·w·cos θR
  - R→R = vol·(w·sin θR + (1 − w)·max(1e-5, √2·sin θpan))
  - vol = 0 gives all zeros.

  **Inferred** (port order `PanMode`, `Pan`, `StereoSplitPanL`, `StereoSplitPanR`, `Volume` in
  `0x102721d1c`): w is the split-mode weight (0 Stereo, 1 Split Stereo). Stereo mode is
  then a balance-type constant-power law normalised to 0 dB at centre. At hard pan the
  near channel is +3.01 dB and the far channel is −100 dB (1e-5), not silent. Split Stereo
  pans each input channel separately with sin/cos and no √2. Ramp lengths and the mode
  switch smoothing were not established.
- **Crossfade assign** (✓ `0x101aedff0`, `0x101aee124`, `0x101aede40`, `0x101aed36c`):
  - A state change ramps a value s′ = 1 − state over 0.002 s × sample rate:
    A → +1, None → 0, B → −1.
  - When the ramp ends, the crossfade factor is switched off if s′ = 0. A track assigned
    None therefore gets no crossfade factor.
  - Otherwise the factor is a 129-point table over crossfader × s′ ∈ [−1, 1].
  - The table comes from the set's `CrossfadeCurve` (`LiveSet/CrossfadeCurve`, 2 in the
    default set). The enum names (`0x102672204`) and helpers (`0x101aed36c`) pair by index:
    0 Dipped (NormalDip), 1 Intermediate (SlightDip), 2 Constant Power, 3 Slow Fade
    (Dipless), 4 Slow Cut, 5 Fast Cut, 6 Transition.
  - Curves 0–5 multiply the gain. Curve 6 multiplies the position before curve 1
    (byte table `0x105bb3a43` = 1,1,1,1,1,1,0).
  - Curve formulas are pseudocode except Dipped (✓ `0x101aee8b8`, edges ±0.95).
- **Sends:** the send matrix (`0x101b18bb4` → `0x101b10efc`, pseudocode) applies no curve.
  Where sends get curve 0 and the floor was not traced. `OConvertLevelProcessor` is the
  candidate (inferred).

## Per-track-type differences

Observed unless marked. The six track kinds share `TrackDevice`, except Main
(`MainTrackDevice`), and share one constructor, ranges and display.

- **Main:** adds `Tempo`, `TimeSignature`, `GlobalGrooveAmount` (shipped range 0–131.25) and
  `CrossFade` (−1…1, default `0` shipped), and holds no sends.
- **PreHear** (cue): has the full mixer, no sends, and its `Volume` is the cue level (`Preview Volume`
  string, inferred). Shipped values include +6 dB.
- **Return:** has sends to every return, itself included, all with `EnabledByUser` false in shipped
  files. Inferred: return-to-return sends start disabled. Where that default is set is
  not traced.
- **Audio, MIDI, Group:** one enabled send per return in shipped files.
- **Chains:** rack chains use `AudioBranchMixerDevice` (`Volume`, `Panorama`, `SendInfos`) and
  are outside this packet.

## Limitations

Static evidence only. A store or a formula in code does not prove that the path runs for
a given track. The logic → engine port values and the UI bindings were not traced.
Branches marked ✓ were confirmed against disassembly in kept dossiers; everything else
comes from C1 pseudocode. Ghidra `FUN_` names are generated; demangled names from the
symbol table are evidence, not proof. `derive_curves.py` emulates float32 with Python
doubles rounded per operation, so last-ulp differences from Apple libm are possible.
Shipped documents are 12.4d1/12.1d1 writes, not 12.4.3 saves.
