## Execution loop

1. Read the canonical owner and choose one concrete unresolved behavior.
2. Verify existing source pins; retain new source bytes only where the gap needs
   them. Keep current/manual-version drift distinct from exact-build evidence.
3. Draft or revise requirements and acceptance cases, then freeze the packet.
4. Dispatch a separate reviewer; correct unsupported claims, missing case kinds,
   circular evidence and overbroad completion claims. Retain review findings.
5. Root updates the spec/research indexes, feature map, verification coverage,
   question register, execution state and append-only log in the same batch.
6. Run the current successor source/delta/link/hash checks. Retain older checker
   results as revision-qualified history; replay only for a concrete current
   dependency, failed required check or release gate under design revision8.
   Regenerate the existing requirements
   browser when its source set changes; run its existing tests if its code changes.
7. Select the next packet by the [revision 4 rule](#selection-rule-replaces-revision-3s). Continue
   independent work around deferred evidence; never mark a deferred area
   complete to drain the queue.

Each reviewable batch names authored requirements, graded/ungraded cases,
source identities, review disposition, remaining unknowns and next packet.
A packet may finish as a partial draft without closing its family.

## Revision 4 — analyst depth throughput (2026-10-20)

Adopted by user direction on 2026-10-20 after a throughput assessment: make
specification depth faster; the specification is finished before T1 is
implemented ("t1 shouldn't be implemented until spec is done"); depth starts
from call chains that show the structure and interaction of the components
involved. This supersedes revision 3's vertical-slice ordering on one point:
the candidate no longer supplies the depth demand signal. T1.6 stays provisioned
and idle; T1.7 is not selectable until the whole-product closure gate is met or
the user re-sequences. Scope, the denominator, ADR 0002/0003/0005, the review
and closure rules and the depth numerator (design revisions 9–11) are unchanged.

### Measured throughput that motivated it

| Measure | Value |
| --- | --- |
| Corpus owner r4 → r7, manifest freeze times | 05:56 → 11:02 UTC on 2026-10-20, 5 h 06 min |
| Released Corpus cases v1 → v5 | 24 → 27; R7 holds 33 cases, 29 finite, 4 U |
| Review files named for Corpus under `full-spec-v1/reviews/` | 279 |
| Corpus modal omissions still open | 176 |
| [Program-structure atlas](program-structure.md) last updated | 2026-10-17; no depth packet since then changed it |

That is roughly one graded case per owner revision, each revision carrying its
own independent review, root catalog update, full lint replay over 2,133
payloads and a preparation/peer chain before one extracted call. The cost per
graded outcome, not harness time, bounds depth.

### Rules

1. **Integration before components, structure before grading.** Depth does not
   start inside a component chosen in isolation, because nothing yet records how
   the components integrate. The first depth packet is one cross-component
   integration map of T1's first integrated scenario, traced end to end: document
   load, transport start, quantized clip launch, playback through the mix graph
   and device chains, recording into Arrangement, save/reopen and export. From
   the scenario's entry points (command registry, document fields, engine
   callbacks) follow the retained call index (`r2/c1-live-v1` calls, indirect,
   vtables and aliases, 1.6 M call edges; the browse per-function caller/callee
   lists) across every component the scenario crosses; record the state and
   data crossing each boundary and which component owns each transition. Family
   call-chain maps are then cut from the integration map, cite it, and classify
   each behavior in the owner's requirements as X-route (lives in self-contained
   functions), S-route (static only) or no-route under ADR 0003. Every structure
   packet updates the [program-structure atlas](program-structure.md) in the
   same change and feeds the route ledger (rule 5), and is reviewed once as a
   structure packet. A static call graph establishes neither execution order
   nor audio routing; mark each edge observed, inferred or unknown. Amended
   the same day: see [indirect-call resolution precedes the map](#amendment--indirect-call-resolution-precedes-the-map-2026-10-20).
2. **Batch grading.** An X packet grades one enumerated set in one harness
   sweep: all parameters and modes of a device, all U cases of a current
   release, or all leaf functions of one map. One frozen manifest, one
   independent review, one root catalog update. Single-case owner successors
   are not selectable except to record a reviewed blocking finding. Amended
   2026-10-21: the batch review admits the batch's observations; see the
   [second amendment](#second-amendment--batch-adoption-authorization-scope-and-x-count-ordering-2026-10-21).
3. **Standing harness authorization.** Calls of self-contained functions through
   the existing [xexec harness](../../tools/xexec/xexec.py) with recorded inputs
   and recorded stubs, which [ADR 0003](../decisions/adr-0003-no-reference-execution.md#extracted-execution-of-original-code)
   already permits, need no per-run preparation, preflight or peer approval. The
   batch manifest records every call: slice hash, address, inputs, stubs,
   harness source hash, timeout and result. The preparation/peer chain remains
   for runs outside the harness call model: patched code, original object
   construction beyond the harness, or new tooling. Amended 2026-10-21: static
   reads of retained bytes belong to the standing class, and a standing packet
   carries one review; see the [second amendment](#second-amendment--batch-adoption-authorization-scope-and-x-count-ordering-2026-10-21).
4. **Parallel harness sessions.** The single-provider limit covers the Ghidra/REA
   project writer only. The harness needs gcc, gdb and the x86_64 slice, so X
   packets run in parallel sessions, one packet directory per device or family.
5. **Route ledger (D-00 reinstated).** One bounded ledger per family, produced by
   rule 1, counts required outcomes by route: X, S or none. It is inventory, not
   completion; it records remaining unsupported work under the confirmed closure rule.
6. **Capability gate D-01 is answered.** Device DSP beyond the five released
   bundles can be graded by extracted execution: R7 holds 29 finite cases from
   it. The Corpus profile stays partial; its open omissions enter the batch
   queue under rule 2 after a Corpus call-chain map under rule 1. D-03 continues
   as the in-binary feasibility gate and opens D-04 by batch where a release
   needs the device.
7. **Incremental checks and predecessor pinning.** Checkpoint lint, whitespace
   and hash replays cover payloads changed since the last passing run; a full
   replay precedes a release or follows a user request. An owner revision pins
   the predecessor's frozen manifest hash instead of copying its spec snapshot.

### Amendment — indirect-call resolution precedes the map (2026-10-20)

Measured on the retained `c1-live-v1` index before any structure packet was
selected: 1.6 M direct call edges over 323,567 functions; the highest in-degree
callees are allocators, guards and abort; with the top 1,000 hubs pruned, forward
reach from a typical function is about 2 functions after six hops and backward
reach about 8; 268,015 indirect call sites in 98,328 functions, of which 25,071
have a resolved target; 80 recovered vtables. The direct-call index does not
carry cross-component flow. Virtual dispatch does, and most of it is unresolved.
Rule 1 therefore runs with these prerequisites and this procedure:

1. **Component layer from symbols first.** Cluster functions by qualified alias
   labels (91,903 primary/symbol field occurrences, including repeated labels;
   39,700 `ableton::` occurrences, then `flip`, `boost`, `std`), the vtable
   symbols and the mangled type-name strings. The
   [atlas](program-structure.md#lexical-component-candidates) separates occurrence,
   distinct-label and function-entry units. This is the
   component inventory and class membership, produced without traversal.
2. **Resolve indirect calls at class level.** Recover vtables from constructor
   stores and RTTI in the retained exports and the binary; attach slot edges to
   every implementation. The structure packet reports the count of indirect sites
   with a resolved target (now 25,071 of 268,015) as its progress measure; the
   count is inventory, not coverage, and closes no outcome. A Ghidra re-export,
   if used, goes through the single native provider; no new tooling is installed
   for it ([ADR 0003](../decisions/adr-0003-no-reference-execution.md#extracted-execution-of-original-code)).
3. **Search bidirectionally and bounded.** Forward from the scenario's entry
   points (command registry, UI bridge, document load) and backward from known
   sinks (device render entries, the audio callback, the file writer); hubs
   pruned; iterative deepening with a per-level budget and a review of each
   frontier. An unresolved indirect site is recorded as an unknown edge, never
   treated as a dead end.
4. **Collapse to inter-component edges before drawing.** Function-level edges
   stay as evidence behind each component edge with observed, inferred or
   unknown status.
5. **Depth-first slicing only afterwards**, for specific paths through the
   component graph.

Selection rule item 1 becomes two packets: 1a, the component layer and
indirect-call resolution with the resolved count reported; 1b, the integration
map. Nothing else in this revision changes.

   existing route: observations through the revision 5 observation packet,
   static findings through the usual standing-packet adoption. There is no
   combined packet, no extra review and no required ordering. Either worker
   uses the other's results whenever they help: an observation shows static
   work where to look, and static work suggests what to probe next.
3. **Conflicts.** If O and S disagree on a unit, both are kept and the owner
   gets an open question, as design revision 14 already requires.
4. **One guest.** One worker drives the guest at a time. Static and X workers
   stay on the host. Static work alongside a sitting is allowed, which relaxes the
   [sitting-first routing](full-live-specification-design.md#confirmed-windows-handoff-and-sitting-first-routing--2026-10-23)
   rule that no static work runs alongside Windows.
5. **Order.** First: Session 0 and Session A of the
   [Windows sitting](phase4-probe-batch.md#windows-guest-adaptation-and-first-sitting--2026-10-22),
   with static work on the document container and save path, transport
   state, mixer values and MIDI note storage. Then the T1 scenario families in
   revision 5's order, each sitting with static work on the same components.
6. **gdb for introspection.** The X worker uses gdb as the
   [gdb introspection method](extracted-execution.md#gdb-introspection--2026-10-23)
   describes: coverage and exit paths for every target by default, and the
   other techniques when a question needs them. A failed or unattempted
   history may be rerun under gdb to find out why; the original result stays
   recorded. The first X task under this rule builds the reusable tracer and
   symbol file that page describes. *Added 2026-10-23 by user direction: "gdb
   is useful for introspection"; expanded the same day into the method page.*
