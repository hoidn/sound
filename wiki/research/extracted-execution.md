# Extracted execution of original Live code (packet X1)

**Question.** [ADR 0003](../decisions/adr-0003-no-reference-execution.md#extracted-execution-of-original-code)
permits running self-contained functions of the shipped x86_64 slice on the Linux
workstation. Can a small harness do this, and do the functions agree with
expectations we have already released?

**Answer (X, draft).** Yes. The harness loads the slice at its own addresses and
calls single functions with System V arguments. Every pilot run completed without
a trap or a fault, and every released expectation it checked agrees:

| Target | Released cases checked | Agreement | Spec examples |
| --- | --- | --- | --- |
| Mixer dB and pan text ([mixer-values-v1](../../handoff/mixer-values-v1/spec.md)) | The 27 of 37 cases with dB or pan text, 44 text checks | 44/44 | 23/23 |
| MIDI map-mode values ([midi-config-v3](../../handoff/midi-config-v3/spec.md), MT cases) | MIDI-CONFIG-110 to 127 (18 cases, 75 values) | 18/18 cases | — |
| Transport number text ([transport-state-v1](../../handoff/transport-state-v1/spec.md)) | TS-006, 008, 009, 020, 021, 022 (8 checks) | 8/8 | 22/22 |

No released expectation disagreed, so no disagreement needed resolving. The
harness found three things the released texts do not cover. First, REQ-TRANSPORT-STATE-011
read literally gives a different text from the code next to powers of ten. Second,
arm64 fuses one multiply-add that x86_64 rounds twice. Third, the 1e-6 value tolerance
cannot hold for a wide parameter range. See [findings](#findings-beyond-the-released-cases).

Evidence: [x1-extracted-exec-v1](../../analysis/ableton-live-12.4.3/r2/x1-extracted-exec-v1/manifest.json),
regenerated by `sh run.sh`. It holds `results/{mixer,midi,transport}.json` (per case),
`raw/runs.jsonl` (argv, stdout and stderr of all 476 runs), `imports.txt` (every
imported symbol and its binding), `addresses.json` (functions and how each was
matched), `x86-disasm.txt` (objdump of every function called), `summary.txt` and
the scripts. The harness is [tools/xexec](../../tools/xexec/xexec.c).

## Method

**Slice.** `/var/tmp/sound-analysis/helpers/Live_x86_64/Live_x86_64.x86_64`,
SHA-256 `1bae9a97…be999b0` (checked), image base `0x100000000`. The load commands
use `LC_DYLD_INFO_ONLY`, not chained fixups. Addresses below are image VAs.

**Loader** ([xexec.c](../../tools/xexec/xexec.c), gcc 13.3, built to
`/var/tmp/sound-analysis/xexec/xexec`):

- It maps `__TEXT`, `__DATA_CONST`, `__DATA` and `__LINKEDIT` at their vmaddr with
  `MAP_FIXED_NOREPLACE` and gives each its initial protection. `__bss` and `__common`
  are zero-filled.
- It walks the rebase opcodes (789,951 pointers). The slide is 0, so they change nothing.
  It applies the bind and lazy-bind opcodes, resolving lazy binds at once.
  Weak binds are not applied, so the slice keeps its own weak definitions.
- Each imported symbol gets a stub. 85 code symbols and the data symbol
  `___stack_chk_guard` are bound to glibc or a small adapter. The other 1,796 symbols
  go to a trap that prints `TRAP <symbol>` and exits.
- A bound stub counts its calls, and every run reports `used <symbol> N`.
- Static initializers do not run. A run calls the ones it needs like any other function.
- An assembly thunk loads six integer and eight xmm registers, calls the
  address and prints `rax`, `rdx`, `xmm0` and `xmm1`. It then prints every
  buffer it passed and any memory requested by an expression
  (for example `b0*+16`, `b0*+4@`). Live's own UTF-16 strings are decoded from
  that memory: refcount at +0, byte size at +4, text at +16. `xexec.py` also
  decodes the libc++ `std::string` layout, but no pilot function returns one.

**Bindings to Linux.** Each binding keeps the contract the call site relies on:

| Group | Symbols | Note |
| --- | --- | --- |
| Memory and strings | `memcpy`, `memmove`, `memset`, `memcmp`, `bzero`, `strlen`, `strchr`, `strcmp`, `strncmp`, `malloc`, `calloc`, `realloc`, `free`, `operator new`/`new[]`, `delete`/`delete[]` | Live's own pool allocator runs unchanged on top of `malloc`/`operator new` |
| libm | 57 functions, including `log10f`, `log10`, `__exp10`, `fma` | Results are glibc 2.39's, **not Apple's**; see [limits](#limits) |
| Stack protector | `___stack_chk_guard` (a variable), `___stack_chk_fail` (prints and exits) | Never fired |
| C++ ABI | `__cxa_guard_acquire`/`release`/`abort` (single-thread Itanium guard), `__cxa_atexit` (accepts, never runs) | |
| Locale and formatting | `newlocale` (C or NULL name only, which macOS treats as C), `vsnprintf_l` (glibc `vsnprintf` under `uselocale`) | The C locale; any other name traps |
| Threads | `pthread_key_create`, `pthread_getspecific`, `pthread_setspecific` (key widened from glibc's `unsigned int` to macOS's `unsigned long`) | Single-threaded |

These imports were actually called (from `results/*.json`, `replaced_imports_called`):

| Target | Imports called |
| --- | --- |
| Mixer | `log10f`, `__exp10`, `vsnprintf_l`, `newlocale`, `strlen`, `strchr`, `malloc`, `operator new`, guards, `__cxa_atexit` |
| MIDI | `operator new`, guards, `__cxa_atexit`, `pthread_key_create`, `pthread_getspecific` |
| Transport | `log10`, `vsnprintf_l`, `newlocale`, `strlen`, `strchr`, `malloc`, `operator new`, guards, `__cxa_atexit` |

**Driver** ([xexec.py](../../tools/xexec/xexec.py)). Each call sequence runs in
its own process with a 20 s timeout, so a fault or a trap ends only that run. With
`skip={addr: [gdb expressions]}` the same process runs under gdb. Each time
execution reaches `addr`, gdb prints the expressions and leaves the function with
`return`, so its body does not run. The pilot uses this once, to stop the 14-bit
receiver before it touches parameter objects.

**Harness problems met on the way.** Each was a missing setup step, not a
difference in the original code. Traps named `_newlocale`, `___cxa_guard_acquire`,
`___cxa_atexit`, `_pthread_key_create` and `_pthread_getspecific`, in that order,
and each was bound as above. A fault at `0x1011a7c89` came from the shared empty Live
string, which a static initializer normally creates. Calling that initializer,
`0x1014206e0`, fixed it.

## Results per target

### Mixer value text

**Setup.** One run per value:

1. Call `0x1014206e0` (empty string).
2. Call `0x1024fb0b0` with (3, 1, 1, 1), exactly as the track constructor does.
3. Call `0x1022736b0`(sret, holder, gain), or `0x101433f60`(sret, pan) for a pan.

The value passed is the case's binary32 value, widened exactly.

**X, agreeing.** Every value text of every released case agrees
(`results/mixer.json`):

- MIXER-VALUES-001: all 17 texts (`0.0 dB`, `C`, `50L`, `50R`, `-inf dB` on every mixer).
- MIXER-VALUES-002 to 017, volume and send:

  | dB text | Cases |
  | --- | --- |
  | `-6.0 dB` | 002 |
  | `-2.654 dB` | 003 |
  | `-6.021 dB` | 004 |
  | `-12.041 dB` | 005 |
  | `6.0 dB` | 006, 014 |
  | `-inf dB` | 007, 010 |
  | `0.0 dB` | 008, 016 |
  | `-69.6 dB` | 009, 017 |
  | `-10.25 dB` | 011 |
  | `-29.0 dB` | 012 |
  | `3.522 dB` | 013 |
  | `-20.0 dB` | 015 |

- MIXER-VALUES-018 to 027, pan and split pans:

  | Pan text | Cases |
  | --- | --- |
  | `30L` | 018 |
  | `C` | 019, 020 |
  | `1R` | 021 |

- All 12 dB and 11 pan examples of REQ-MIXER-VALUES-006 and 007 agree.
- Not run: the track-switch texts `On` and `Off` (001, 030), the code names (028, 029,
  031 to 036) and the crossfader value (037).

**`log10f` substitution.** The text rests on glibc's `log10f`, not Apple's. For the 14
distinct positive gains, glibc's result is correctly rounded for 12. It is one ulp off
for 0.30725 and 0.7367056608. Running the formatter alone with L − 1 ulp, L and L + 1 ulp
gave the same text for all 14 gains. Inferred: no released mixer text depends on which
`log10f` is used, provided it is within one ulp.

**Static arm64 comparison** (dossiers s9-0001/0002, `x86-disasm.txt`):

- Gain → text: `fcvt s0,d0`, `log10f`, `fmul` by 20.0f, `fcvt d0,s0` (arm64), against
  `cvtsd2ss`, `log10f`, `mulss` 20.0f, `cvtss2sd` (x86). There is no fused operation.
  The guard for gain ≤ 0 → −140 is the same.
- dB formatter: `min + 0.3` (`0x3fd3333333333333`), compared with `>=` in both slices.
  Rounding to the chosen decimals uses `frinta` on arm64 and `roundsd(x + copysign(0.49999999999999994, x), trunc)`
  on x86. Both round half away from zero.
- Number formatter: both replace a value that rounds to 0 with +0, then call
  `vsnprintf_l` with `%*.*f`.
- Pan: the same constants.
- **Possible slice difference:** Apple's arm64 and x86_64 `log10f`, `__exp10` and
  `vsnprintf_l` are different builds and were not compared. Nothing else differs.

### MIDI map-mode values

**Setup.**

1. Call the unit's static initializer `0x101bc1360` before the value function.
   Without it, the accel tables are empty. The control run shows this:
   AccelSignedBit v = 1 from 0.5 gives 0.578125 (default step 20) instead of 0.50390625.
2. Call `0x101bb27b0` once per message. The arguments are: current value; {min, max}
   as two floats in `xmm1`; data {v, prior = `FLT_MAX`, mode, sensitivity 1.0}; quantized
   = the case's `stepped`; reversed = 0. The returned value becomes the next current value.
3. For Absolute14Bit, each case runs in one process under gdb. The original setters
   `0x101bbc830`/`0x101bbc980` and the combiner `0x101bbc870` hold and pair the halves.
   The combiner's call to Apply `0x101bbc9c0` is skipped, and the data it would have
   received is recorded. Receiver state: no half held. The prior is the input's last
   value on that controller, or −129 before any.

**X, agreeing** (`results/midi.json`). All 18 value cases agree within the released
1e-6:

| Cases | Modes |
| --- | --- |
| 110 (MT-01) | Absolute |
| 111–114 (MT-02 to 05) | Absolute14Bit, including the newer MSB replacing the held one and a lone LSB |
| 115–118 (MT-06 to 09) | The four linear modes |
| 119–122 (MT-10 to 13) | The four accel modes |
| 123 (MT-14) | Clamping |
| 124, 125 (MT-15, 16) | Stepped parameters |
| 126 (MT-22) | Crossfader |
| 127 (MT-23) | A single relative step |

In the 14-bit cases the pairing that the code performed matched the released rule:
every completed pair delivered v = pair/129 (bit-equal to the spec rule), with mode
0 and sensitivity 1. The halves were cleared after each pair.

**Scope.**

- The value function, the decoder and the 14-bit receiver ran. Message routing,
  the per-input last-value table, Apply, takeover and the parameter setter did not.
- For stepped relative cases, the receiver's accumulator was not run. With
  sensitivity 1 it fires on every message
  ([MIDI transforms](midi-transforms-native.md#per-mode-transform-table)), and the
  harness assumes that.

**Static arm64 comparison** (dossiers n7-0001 to 0004, `x86-disasm.txt`):

- **Absolute uses FMA on arm64.** `0x101b76c60 fmadd s0,s9,s0,s1` computes
  max·t + min·(1 − t) with one rounding of the sum. x86 `0x101bb2825`–`0x101bb282d`
  rounds max·t and min·(1 − t) separately and then adds. With min = 0, as in every
  released case, the results are identical.
  - An exact-rational model of the x86 sequence reproduces X for all 128 data values
    at (−1, 1) and at (20, 999).
  - The arm64 `fmadd` model differs from X for 0 of 128 values at (−1, 1), and for
    35 of 128 at (20, 999), each by one binary32 ulp, at most 6.1e-5 (`fma_check`).
- **Relative step order.** arm64 forms (max − min)/256 · (d·s). x86 forms
  ((max − min)/256 · d) · s. They are identical for s = 1, the only released
  sensitivity.
- **Rounding.** A quantized result uses `frinta` (arm64) and the
  `roundss` + copysign(0.49999997) sequence (x86). Both round half away from zero.
  A quantized relative step is ±1 in both (`fcsel` versus table `0x105d5dbf0` = {−1, 1}).
- **Constants and clamping.** Constants are equal: tables A and B, 1/256, 129 and
  the prior fill −129 (`native-constants.json`). Clamping has the same order in both.

## Findings beyond the released cases

These inputs lie outside the releases. They are X results with the substitutions above.

- **REQ-TRANSPORT-STATE-011 step 1 is imprecise next to powers of ten.** The code takes
  k from the binary64 `log10`, which rounds log10(1000.0000000000001) to 3.0. The
  spec's "smallest integer not below log10|x|" gives 4. The two give different texts:

  | Value | X | Spec rule, read with exact log10 |
  | --- | --- | --- |
  | 10.000000000000002 | `10.0000000000000018` | `10.000000000000002` |
  | 1000.0000000000001 | `1000.00000000000011` | `1000.0000000000001` |
  | 1000000.0000000001 | `1000000.00000000012` | `1000000.0000000001` |
  | 0.09999999999999999 | `0.099999999999999992` | `0.0999999999999999917` |
  | 0.009999999999999998 | `0.0099999999999999985` | `0.00999999999999999847` |

  The pattern holds for any binary64 value just above 10ⁿ (n ≥ 1) or just below 10⁻ⁿ.
  The texts agree for 0.9999999999999999 and for tested binary32 tempos. Inferred: Apple's
  `log10` gives the same integer, because the correctly rounded result is that
  integer. A later spec revision should define k from the rounded binary64 `log10`
  or exclude these values.
- **Negative zero** is written `-0` by both writers. REQ-011 leaves −0 undefined.
- **Int parser** (REQ-006 unknowns in [Q-012](../questions.md#q-012-transport-state-load-and-save-semantics)):

  | Text | Parser result |
  | --- | --- |
  | ` 201 ` | refused |
  | `+201 ` | refused |
  | `-201` | accepted as −201 |
  | `- 201` | refused |
  | `+` | refused |
  | `-` | refused |
  | `2147483648` | refused |
  | `4294967497` | refused |
  | 63-character `0…0201` | 201 |

  What the loader then does with −201 is not shown.
- **Pan ties** (excluded by REQ-MIXER-VALUES-007): −0.75 → `38L`, −0.25 → `12L`,
  0.25 → `12R`, 0.75 → `38R`. These are ties to even, from `%.0f` in glibc. Inferred, not
  shown: Apple's `vsnprintf_l` also rounds exact ties to even, so the text would be the same.
- **The −69.7 dB edge** (excluded within 0.00005 dB): the binary32 dB value
  −69.69999694824219 gives `-69.7 dB` and −69.70000457763672 gives `-inf dB`. The text
  side therefore has no uncertainty for binary32 dB values; only `log10f` near that
  gain does.
- **Value tolerance.** REQ-MIDI-USER-005's 1e-6 absolute tolerance fails for wide
  ranges: near the top of (20, 999) one binary32 ulp is 6.1e-5. The x86 and arm64 slices already
  differ by that much (see FMA above). No released case has such a range.

## Limits

Per [ADR 0003](../decisions/adr-0003-no-reference-execution.md#extracted-execution-of-original-code):

- **What X shows.** X shows what these x86_64 functions compute for these inputs with
  this setup. It does not show that Live reaches them for a document, which UI surface
  shows a text, or which state the application holds there. Call paths are static
  evidence on the cited pages.
- **Slice.** The release target is arm64. Equivalence is inferred from the static
  comparisons above. Known divergence is limited to the arm64 `fmadd` in Absolute
  mode with min ≠ 0, and to Apple library builds that were not compared.
- **Substituted libraries.** Every `libm`, `vsnprintf_l` and `newlocale` result is
  glibc 2.39's. For `log10f` that was measured: 2 of 14 results are not correctly
  rounded. The ±1 ulp check bounds its effect on the mixer texts. `log10` and `%f`
  formatting are correctly rounded in glibc; Apple's were not available.
- **Setup is the harness's.** It runs the static initializers it calls and none
  other. Object states are hand-built (the 14-bit receiver) or come from the original
  constructors (the dB holder). The process is single-threaded and runs in the C locale.
- **Not run.** Exceptions, Objective-C, `%gs` thread-local storage and calls with stack
  arguments were not needed and are not supported.
- **Reruns.** Heap addresses in `raw/runs.jsonl` vary between runs (ASLR), so the
  manifest is not byte-stable. The results files are.

| P4-N5-01, P4-H4-04, P4B-CORPUS-01 (device parameter domains, labels, Corpus DSP) | The code lives in device bundles. These need slide support for images not at their vmaddr (the rebase walker already takes a slide) and Accelerate bindings if vDSP is used. |
| PRB-N8-05 (MultiF0 fields) | The built-in MultiF0 in Live x86_64 is self-contained numerics, but large. It probably needs vDSP or FFT bindings. Stretch goal. |

Not settleable this way: launch, process, socket, timing, UI and file-system
probes (PRB-N4, H1, H2-01 to 03 and 05 to 09, P5, PRB-N8-01 to 04, PRB-N2, S4-01 to
03 and 14 to 16, ESC-N3-01, S5-04 and 05, S8-08 and 11, S9-08) and the incomplete
records P4B-H6-01 and P4B-T1-01.

## Reproduction

```sh
sh analysis/ableton-live-12.4.3/r2/x1-extracted-exec-v1/run.sh
```

This needs gcc, gdb, objdump and python3. `XEXEC_SLICE` and `XEXEC_BIN` override
the slice and loader paths. A run takes about 40 s and starts 476 processes.
