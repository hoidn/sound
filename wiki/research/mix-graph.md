# Mix graph and automation in playback (packet T1.4)

**Question.** For T1's offline render
([ADR 0004](../decisions/adr-0004-target-scope-t1.md)): in which order does a track's
signal pass the device chain, the volume, pan and crossfade gains and the sends; how are
returns and the main track summed; what do mute and solo do; when and how often are gain and
automation values applied; and does this settle
[Q-019](../questions.md#q-019-mixer-volume-and-send-values-sent-to-the-engine)?

**Answer (draft).** The track's output stage is one set of engine processors per track. It
forms a 2×2 main matrix (pan law × volume gain × the on switch) and one 2×2 matrix per send,
and applies them to the device-chain output once per sample. Gains change only through ramp
events: linear ramps of a stated sample length. A pre-fader send carries the device-chain
output times the send gain only. A post-fader send also carries the pan law and the volume.
Every source adds into its destination's input. Mute and solo act through one switch word per
track that turns its main output and its sends on or off over 75 samples. The engine plays
automation itself, from a point list the logic layer sends: linear in sample time between
points, delivered as ramps of 200 to 65,536 samples. Q-019 is **settled statically with
conditions**: the logic layer sends fader positions, and the engine applies the fader curve,
the crossfade factor and the silence floor. Two existing claims are wrong for playback: the
automation spec's A1 (stored units) for volume and send envelopes, and its exact curve values,
which playback replaces by a 16-piece polyline.

**Method.** The x86_64 `Ableton Live Engine` bundle is a named compile of Live's audio engine
([x86-only bundles](x86-only-bundles.md#consequence-for-analysis-a-named-copy-of-lives-engine-code)).
Its processor classes (`OTrackOutVolumeProcessor`, `OCrossFadeVolumeProcessor` and others) were
read under their names. Each function that was run was then located in the Live x86_64 slice.
The matches use the same size in `LC_FUNCTION_STARTS` and at least 87 % identical bytes
(`match_engine.py`; the differing bytes are RIP-relative displacements and call targets). Inside the track-output region a constant address offset (0x1019cf310)
holds for every function checked. Live's own named `__invoke` thunks link handlers to ports in
both Live slices. The engine bundle itself was not executed: its image base is 0, which the
loader cannot map.

## Track output stage

**S (pc), wiring from the Live x86_64 builder `0x102866450`** (the `ATrackOutUnit` compound; arm64
`0x102731438`):

- **Inputs.** The device chain's output enters `OTrackOutProcessor` at `InL`/`InR`.
- **Pan and volume.** `PanMode` passes through a ramp node to the `PanModeAmount` input
  of `OTrackOutVolumeProcessor`. `Pan`, `StereoSplitPanL`/`R` and the volume gain (from
  `OCrossFadeVolumeProcessor`) go directly to that processor.
- **Switches.** `Speaker` and `SoloPrehear` feed `OTrackOutSwitchesProcessor`. It makes a
  switch word, and a splitter turns that word into `MainOn`, `SendsOn` and `PrehearOn`. Each of
  those passes through a ramp node.
- **Sends.** `PrePostState` passes through a splitter to `SendIsPost<k>`, then a ramp node per
  send. `Send<k>` goes to `Send<k>`.
- **Outputs.** `OTrackOutVolumeProcessor` sends the main matrix and 12 send matrices to
  `OTrackOutProcessor`. That processor writes `OutL`/`OutR` (main), 12 send outputs, meter and
  pre-hear outputs.

**Main matrix (X, with S composition).**

- **Pan law.** The volume-panner block holds five ramped inputs: `PanModeAmount`, `Pan`,
  `SplitL`, `SplitR` and the volume gain. On any input event every input advances to the
  current sample and the new ramp is set. The recompute (engine `0x158510`, Live
  `0x101b27860`) then takes the smallest non-zero remaining ramp length L. It extrapolates
  every input to L, evaluates the pan law there (`TVolumePanner::Calc`, the X2 function
  `0x101b719e0`), and sets the four outputs to ramp to those values over L.
- **X run of the pan law.** A volume ramp from 1 to 0.5 over 100 samples gives outputs
  (0.5, 0, 0, 0.5) over 100. A pan ramp to −1 over 50 samples, started at sample 20, gives
  (0.919239, 0, 0, 6.5·10⁻⁶) over 50. That is the pan law at pan −1 with volume 0.65, the
  volume extrapolated to sample 70.
- **Switch.** `TVolumeSwitch::Calc` (`0x101b40cf0`) multiplies the matrix by `MainOn`. X: on 1
  gives the matrix, on 0 gives zeros, on 0.5 gives half.

**Sends (X; layout S).**

- **Inputs.** `TSendVolumes::Calc` (`0x101b40d30`) takes 13 inputs:
  - 0: `SendsOn`
  - 1: the send-k-active bit (`SendOutsConnected`)
  - 2: `SendIsPost`
  - 3: the send gain
  - 4–7: the track's pan-law matrix
  - 8: `GroupOn`
  - 9–12: a group matrix
- **Defaults.** The constructor (`0x172af0`, pc) sets input 8 to 1 and inputs 9–12 to the
  identity for every send.
- **X result.** out = in3 · in0 · in1 · in8 · (p · (G∘M) + (1 − p) · I), with p = in2, M the
  track matrix, G the group matrix and I the identity. So with p = 1 (post-fader) the send
  matrix is the send gain times the track's pan-law matrix, which includes the volume. With
  p = 0 (pre-fader) it is the send gain times the identity: no pan, volume or crossfade.
  - Values from distinct test inputs: post (0.45, 0.05, 0.1, 0.3), pre (0.5, 0, 0, 0.5).
  - The same with the pan-law matrix of pan −0.5 and volume 0.5: post (0.65328, 0, 0, 0.270598),
    pre (1, 0, 0, 1).
- **Pre/post selection (S, pc).** Live x86_64 `0x1027bde00` turns `LiveSet/SendsPre` into a
  12-bit mask: bit k is `SendPreBool` k, and a thirteenth entry raises "bitset set argument
  out of range". The mask goes to every track's `PrePostState`. The splitter
  (`OTrackOutSplitPrePostStateProcessor::OnIn`, engine `0x171250`) sends `SendIsPost<k>` = 0
  when bit k is set and 1 otherwise. Its initial state forces the first value through.

**Per-sample application and summing (S, pc).**

- **Gains.** `OTrackOutProcessor` holds each gain with a float32 slope. A ramp event (target,
  n > 0) sets slope = (target − current)/n in float32. A slope below 10⁻¹² in magnitude, or
  n = 0, sets the gain at once.
- **Per-sample loop.** The audio functions (`CalcStereo<…>`) take no sample count. The engine
  calls them once per sample between scheduled events. Each sample forms the 2×2 products
  with the float32 input and advances every gain by its slope (float32). The main matrix
  advances before it is used (✓ Live x86_64 `0x101b4d870`); a send matrix is used and then
  advanced (✓ `0x101b4c400`).
- **Ramp ends.** The ramp producers set the end exactly. `OMakeRampProcessor` re-sends
  (value, 0) after its duration. The automation player sends a new ramp at each update.
- **Summing.** Each send output adds (double)(its float32 product) into the destination's
  binary64 accumulator (✓ `addsd`, `0x101b4c400`). The main outputs are float32 values
  (✓ `0x101b4d870`). The receiving `OTrackInProcessor` reads its accumulators once per sample,
  converts them to float32, adds the direct input and clears them (`0x1702e0`, pc). How several
  main outputs reach one input (the main bus) was not followed to the end: the summation order
  and its intermediate precision are unknown.
- **Clipping.** Clipped input variants limit to ±1000. Where they are used was not traced.
- **Ramp interpolator (X).** Binary64 value and slope; `Inc(k)` adds k·slope and stops at the
  end. `SetRamp(target, 0)` sets the value. Values below 10⁻¹² in magnitude read as 0.
  - Example: 0 → 1 over 4 samples gives 0.25, 0.5, 0.75, 1, 1.
  - A slope of 10⁻¹³ jumps at once.
- **Fade time (X).** The ramp nodes for `MainOn`, `SendsOn`, `PrehearOn`, `SendIsPost<k>` and
  `PanModeAmount` are `OMakeRampProcessor` (pc). Their duration is
  `NAudioTraits::STrackFadeTime()` = clamp(G, 10, 4096) samples, with G = 75 unless a developer
  option overrides it. It is a fixed sample count at any sample rate.
- **Crossfade assign.** A change still ramps over 2 ms
  ([mixer values](mixer-values.md#engine-gain-stages)).

## Mute and solo

From [notes-solo.txt](../../analysis/ableton-live-12.4.3/r2/t14-mix-v1/notes-solo.txt); the switch
logic is X.

- **Stored fields (S, pc; D for shipped values).**
  - `Mixer/SoloSink` is the track's Solo/Cue button: member +0x1f0 of `ATrackDevice`, named
    "Solo-Cue", saved.
  - `LiveSet/SoloInPlace` is a saved song member.
  - `LiveSet/SoloOrPflSavedValue` holds the last Solo/Cue switch value; true means Solo.
  - Exclusive solo is a preference, not set content.
  - Shipped values: `SoloSink` false in 290 of 290; `SoloInPlace` true in 25 and false in 1;
    `SoloOrPflSavedValue` true in 26 of 26.
- **Solo types (X).** 0 None, 1 Solo, 2 Following, 3 Muted For Player Solo, 4 Indirectly Muted,
  5 Muted For Return Solo, 6 Prehear. The predicates hold for these types:
  - speaker-irrelevant: {1, 3, 4}
  - solo-or-prehear: {1, 6}
  - muted-for-solo: {3, 4, 5}
- **Switch word (X).** The bits are main on, sends on, pre-hear on and a meter bit. With s the
  speaker state:

  | Type | Word | Effect |
  | --- | --- | --- |
  | 0, 2 | 3s | main and sends follow the speaker |
  | 1 | 3 | main and sends on, speaker ignored |
  | 3 | 0 | silent |
  | 4 | s + 8 | main follows the speaker, sends off |
  | 5 | 2s | sends follow the speaker, main off |
  | 6 | 3s + 4 | as type 0, plus pre-hear |

  Values outside 0–6 behave as 0. The splitter maps bits 0, 1 and 2 to `MainOn`, `SendsOn` and
  `PrehearOn` as 1.0 or 0.0 (X, all 16 words).
- **Logic (S, pc; Live x86_64 `0x10284d180`, arm64 `0x102719f88`).**
  - Without a soloed track nothing changes.
  - Otherwise every non-soloed player or return track becomes 3. With `SoloInPlace` on and no
    return soloed, returns go back to 0.
  - Upstream of a soloed track, feeders become 2. Feeders of a soloed return that were 3
    become 5.
  - Downstream non-returns become 2. A routing edge between two muted tracks makes the source 4.
  - Main and pre-hear tracks are never muted.
  - Cue mode (`SoloOrPflSavedValue` false) gives soloed tracks type 6 and mutes nothing.
  - Edges come from audio routings and from active sends (send holder `mpActive`).

## Automation in playback

From [notes-automation.txt](../../analysis/ableton-live-12.4.3/r2/t14-mix-v1/notes-automation.txt)
and [notes-q019.txt](../../analysis/ableton-live-12.4.3/r2/t14-mix-v1/notes-q019.txt).

- **The engine evaluates (S, pc; ✓ for the send loop).**
  - The logic side sends each envelope as a point list, `OFloatAutomation.Create`
    (Live x86_64 `0x102823cb0`): event times in beats (binary64) and values (float32).
  - The first event's time is replaced by −10,000,000 beats, whatever it was (✓
    `0x102823d84`). In shipped envelopes that event is the leading event at the lower bound L.
  - A curved segment (any control ≠ 0.5) is sent as 15 interior points at Bezier parameter
    s = (i + 1)/16. The engine sees a 16-piece polyline, not a curve.
- **Event lookup (S, pc).**
  - The song beat minus the automation offset is rounded to a grid of 1/3,843,840 beat.
  - The current event is the last event at or before it, so at a step the later event wins.
  - Point times are scheduled as absolute beat events: sample-accurate and independent of the
    buffer size.
- **Segments (X for the arithmetic, S for the drive).**
  - `OFloatAutomationSegment::Init` (`0x101b1f400`) computes slope = float32(v1 − v0) / duration
    in samples (binary64). The value is v0 + max(0, offset)·slope, kept inside [v0, v1].
  - A segment with v0 = v1 is constant.
  - With no next event, or with segment updates off, the value holds.
- **Update rate (S, ✓).** Every timeable gets N = 1000, a 200-sample minimum segment and no
  smoothing from a post-construction hook. No override was found for track-mixer parameters
  (inferred).
  - The player sends ramp events of L = clamp(trunc(((max − min)/1000)/|slope|), 200, 65,536)
    samples along the segment, with (max − min) the engine-side range of the parameter.
  - The last ramp before a point is shortened to end on the line. A new segment starts at each
    point's sample.
  - With the transport stopped L = 0: values jump.
- **Units (S with conditions, Q-019 fork).** Event values pass through the conversion of the
  automation owner's provider, which returns the parameter's own converter.
  - Volume and send values are therefore fader positions, and pan stays in pan units.
  - This contradicts A1 of [SPEC-AUTOMATION-ENVELOPES](../specs/automation-envelopes.md) r3,
    which read the null-converter provider of a different consumer (arm64 `0x10275c5a0`).
  - Volume automation therefore interpolates in fader position. The engine evaluates the
    position-to-gain curve at each ramp end and ramps the gain linearly in between.
  - **Condition:** that the owner at `AListAutomation`+0x130 is the parameter's
    `AFloatAutomationTarget` for a loaded track envelope. Engine consistency supports it: the
    volume input of `OCrossFadeVolumeProcessor` is a position.
- **X comparison with the evaluator of REQ-AUTOMATION-ENVELOPES-010.**

  | Envelope | t | Played (polyline or −1e7 start) | REQ-010 evaluator (X2) |
  | --- | --- | --- | --- |
  | E9 (curve 0.5/0/0.5/0) | 1 | −0.98246047 | −0.983523965 |
  | E9 | 2 | −0.75 (a polyline point) | −0.75 |
  | E9 | 3 | 0.01753953 | 0.0164760482 |
  | E13 (L, 1) → (4, 0) | 0 | 3.9999984·10⁻⁷ | 6.341957714539603·10⁻⁸ |
  | E1 (4, 0) → (8, 1) | 5, 6, 7 | 0.25, 0.5, 0.75 | 0.25, 0.5, 0.75 |

  The 15 E9 points come from the original Bezier evaluator (`0x1011f1610`). The played values
  come from `OFloatAutomationSegment::Init` between the bracketing points at 22,050 samples
  per beat.
- **Session clips (S, pc).** Each track has an automation index: −1 means arrangement, k ≥ 0
  means the playing session slot, −2 means none (for example past the end of an unlooped
  clip). Only Back to Arrangement sets −1 again (engine `0x137690`).
  - With a session clip playing, arrangement automation is not applied. Each parameter takes
    its `Manual` value unless the playing clip has an envelope for it
    (`OAsyncValueTimeable::ActivateAutomation`, engine `0x13d800`).
  - Inferred: after load the index is −1, so arrangement envelopes drive until the track's
    first launch. Return and main tracks have no clip slots, so theirs always drive. T1
    automation is therefore effective on returns, the main track, and tracks before their
    first launch.
  - The clip-envelope time base is not traced.
- **Override (S, pc).** An overridden flag and Re-Enable exist (`OAsyncValueTimeable`
  `0x13dac0`, `0x13e7d0`). Only manual edits set it, which T1 scripts do not make.
  `LiveSet/AutomationMode` is the automation-arm button, not traced.

## Q-019: values on the volume and send ports

From [notes-q019.txt](../../analysis/ableton-live-12.4.3/r2/t14-mix-v1/notes-q019.txt).
**Settled statically, with conditions.**

- **What the logic side sends.** The volume `AUserFloat` stores the gain with an
  `ALevelUserFloatConverter` of kind 1 (✓ `0x10284f013`). The value sent to the engine is
  p = clamp₀₁(SControlLevel(1, g)), the volume-curve position (converter slot +0x28 ✓
  `0x102683d70`). This holds for the manual value, timeable creation and envelope events.
- **What the engine does.** It applies SAudioLevel(1, p). With the crossfade branch it applies
  the crossfade factor (Transition scales p before the curve). Either branch then sets any
  result ≤ 0.00032 to 0 (✓ `0x102853727`). The result is the volume gain input of the pan law.
- **Consequences.**
  - The stored gain round-trips exactly in range (X2).
  - A stored gain above 1.99526238 plays at 1.99526238 (+6 dB).
  - A stored gain below 0.0003162277571, including 0 and negative values, is silent.
- **Sends.** A send's converter has kind 0, the send curve (✓ `0x102788389`). The holder's
  graph builder adds an `AConvertLevel` node of kind 0 (✓ `0x1026f8ccd`), giving SAudioLevel(0, p)
  and the same floor at `Send<k>`.
- **Conditions.**
  1. The envelope owner identity (as above).
  2. The connection of that `AConvertLevel` node to `Send<k>` (pc, not followed to the port).
  3. The test-only identity flag of SAudioLevel is unset.
  4. No arm64 comparison of the envelope and send-graph paths.
  5. The wiring branch (crossfade unit or plain converter) depends on a track virtual method
     (slot 0x370) that was not resolved. With crossfade assign None both branches give the
     same gain.

## Slice comparison

Static, from `fma-scan.txt`:

- **Exact in both slices.** arm64 `TSendVolumes::Calc` (`0x101b10efc`), `SetRamp`, the panner
  recompute and the send recompute have no fused operation.
- **SGroupedVolumes.** The arm64 version (`0x101b3b720`) fuses four multiply-adds. With the
  default identity group matrix every product is exact, so ungrouped tracks agree.
- **Extrapolate.** The arm64 version (`0x101aff494`) fuses value + k·slope in binary64 before
  rounding to float32. A difference needs a binary64 result at a float32 tie. None was observed.
- **Pan law and crossfade.** The fused operations of x2-mixer-v1 still apply: three in the pan
  law, and two in Dipped and Intermediate.
- **Not compared.** The per-sample track-output functions on arm64 (`CalcStereo`) were not
  compared. A fused input × gain + input × gain would differ in the last float32 bit of each
  output sample.

## Corrections to existing pages

Applied on 2026-10-18 in SPEC-AUTOMATION-ENVELOPES r4, SPEC-MIXER-VALUES r4 and a dated
note on [mixer values](mixer-values.md).


- **SPEC-AUTOMATION-ENVELOPES r3, A1.** "Every Float envelope value is in stored units" is
  wrong for Volume and Send envelopes in playback, and probably in the logic evaluator too.
  The provider the event values use is the owner's, and it returns the parameter's converter
  (fader position). Pan cases are unaffected.
- **SPEC-AUTOMATION-ENVELOPES r3, REQ-010 and A2.** What playback applies differs from E(t):
  - Curved segments play as a 16-piece polyline.
  - The leading event's ramp starts at −10⁷ beats, not at L.
  - At a step the last event at t applies (the evaluator's mode 1).
  - A2's drive is now static.
  - REQ-010 remains the logic-side evaluator's value.
- **x2-mixer-v1 `addresses.json`.** It labels arm64 `0x101ac3c94` as position → gain. That
  function is gain → position; `0x101ac3bac` is position → gain. No result depends on it.
- **SPEC-MIXER-VALUES r3.** Five clauses can now be narrowed:
  - REQ-011's condition and REQ-012 are settled by the Q-019 result above.
  - The REQ-013 pan-mode-to-w U becomes S: `PanMode` drives `PanModeAmount` through a
    75-sample ramp. The value mapping 0 → 0, 1 → 1 is inferred from the enum index sent as a
    float.
  - The REQ-013 "pan ramp lengths" U is answered by the ramp rules above.
  - REQ-015's render part follows the clamp of the conversion.
  - The `EnabledByUser` U in REQ-003 now has a candidate consumer: the send-active bit
    (`mpActive`), whose derivation is not traced.

## Unknowns

## Limits

- **What X shows.** X shows what each Live x86_64 function computes for the inputs, with
  glibc `cos` substituted. The composition (which processor feeds which, and when events
  arrive) is static.
- **Engine twins.** The engine bundle served only as a name source. Equivalence of its compile
  with Live's is shown per function by byte similarity, not in general.
- **Release slice.** arm64 equivalence is inferred from the scan above.
- **Not a mix render.** No rendered mix exists.
- **Not byte-stable.** `raw/runs.jsonl` records heap addresses, so the manifest is not byte-stable.
