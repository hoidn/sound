# Web Connector, AddOns and Swapper: static evidence

Packet H6 of [roadmap revision 2](native-decompilation-roadmap.md#revision-2-proposal--2026-10-17),
for FEAT-ECOSYSTEM and FEAT-DELIVERY. Question: what role does each of the three
helper executables in `Contents/App-Resources/Extensions/` play, how is it
launched, and how does it talk to Live and to remote services? Everything here
comes from bytes on disk. Nothing from the bundle was executed, and no URL or
host was contacted. Runtime order, timing and actual network traffic stay
**unknown** until a Phase 4 capture.

## Evidence

Source: [SRC-ABLETON-12-4-3](sources/ableton-live-12.4.3.md), local copy
`/home/ollie/Ableton Live 12 Suite.app` (read-only). Retained run:
[h6-web-v1](../../analysis/ableton-live-12.4.3/r2/h6-web-v1/manifest.json),
regenerated by `sh run.sh` (Python 3.13.9 standard library, `python3 -I`). Two
consecutive runs gave identical hashes for all 64 output files. The manifest
records each script and output with its SHA-256, the helper slice identities
and their decompile coverage.

Each corpus passed `tools/r2_corpus.py corpus` and `indexes`. The helper
function counts are Ghidra's, not source functions. In the tables below a
function or string is cited by its arm64 address, and a bytecode location by
`module:qualname` in `pyc-listings/`.

**Method.** `pyc311.py` parses CPython 3.11 marshal data in pure Python and lists
bytecode with names and constants resolved. It takes its opcode table from the
bundle's own `Python/lib/opcode.pyc`, and it checks eight known opcode values
before it writes any output. `macho_meta.py` reads load commands, code-signature
identifiers and entitlements. `helper_evidence.py` copies the cited strings and
the full decompiled code of the cited functions out of each C1/C2 corpus, so the
evidence does not depend on `/var/tmp`. Limitation: jump targets in the bytecode
listings are raw relative arguments.

## Identity

Observed in `macho-meta.json`:

- All four files are x86_64 + arm64 universal binaries with minimum macOS 11.0
  (SDK 15.5). They are signed with team ID `MWR434WD94`, and their signing
  identifiers equal their file names.
- All four carry the same five entitlements, including
  `cs.disable-library-validation` and `cs.allow-unsigned-executable-memory`.
- None embeds an `__info_plist`, and `Extensions/` contains no `Info.plist`.
  The packet brief expected Info.plists; there are none.
- `Ableton AddOns` links `libonnxruntime_abl.dylib`.
- The `xdelta3` banner is `Xdelta version 3.0.12, Copyright (C) Joshua MacDonald`,
  Apache-2.0. It links only `libSystem`.

All three helpers start by registering the identity
`("Ableton", <name>, "12.4.3", …)` next to `("Ableton", "Live", "12.4.3", "12.0")`.
Each writes its own log: `WebConnector.txt`, `AddOns.txt` or `Swapper.txt`
(Web Connector `entry` 0x10017a128; AddOns 0x100136324; Swapper 0x1001308e0).
**Inferred:** much of each binary is statically linked shared Live library code,
for example pack-database query names in the Swapper and authorization URL builders in
the Web Connector. A string that appears in a helper therefore does not show
that the helper uses the feature.

## Live ↔ helper IPC

Observed:

- Both helpers build the channel address in the same way. It is `ipc://` +
  `temp_directory_path()` + the channel ID, or `inproc://` + ID in one mode
  (Web Connector 0x10017d32c and 0x1008cd9a4; AddOns 0x1001425ac).
- The class names `TNanoMsgIPCChannel`, `TSocketManager::ManageSocket(INanoMsgSocket)`
  and the nanomsg `NN_SIPC`/`NN_BIPC` state strings show that the transport is
  nanomsg's IPC transport.
- The channel ID comes from Live: the `ipc_channel_id` config key for the Web
  Connector, and `--cid` for AddOns.
- Direction labels: `webconnector->live` appears in both Live and the Web
  Connector. `addons->live` appears only in AddOns and `live->addons` only in
  Live. Their role (channel name or log tag) is unknown.
- The Python-visible API is the `AbletonIPC` module: `create_ipc_channel(id)`,
  `send(event, payload)`, `register_event(event, callback(event, payload))`,
  `unregister_event` and `poll` (0x10017b9d4; `ipc_channel.pyc`).
- The shipped IPC test creates a channel named `basename(tempfile.mktemp())`
  and runs an echo client as a child process (`ipc_tests/*.pyc`).

Unknown: the wire framing (the native send goes through a vtable slot that was
not resolved). Also unknown: which side binds the socket ("Can't open out IPC
Channel as server/client" exists in both), and the nanomsg socket type.

**Web Connector events** (Observed, `auto_updates.pyc`, `main.pyc`, `connector.pyc`):

| Direction | Event | Payload |
| --- | --- | --- |
| WC → Live | `update_available` | target version string |
| WC → Live | `vcredist_needs_install` | `''` (Windows) |
| WC → Live | `update_ready_to_apply` | `''` |
| WC → Live | `update_failed` | `''` |
| Live → WC | `continue`, `cancel` | Confirmation; the WC polls once per second when `wait_for_confirmation` is set |

Live's matching log strings include `WebConnector: auto-update available: `,
`… ready` and `… failed: ` (Live arm64 +0x5b1ba21 and +0x5b1ba7b).

**AddOns events** (Observed):

- Live → AddOns (wide-string names in the dispatcher 0x100149504):
  `SetRemoteSettings`, `CheckInstalledAddOns`, `CheckForPreparedUpdateAndInstall`,
  `DownloadLatestVersionForAddOn`, `StopDownloadAddOns`, `DeleteAddOn` and
  `InstallFileForBackend`. They correspond to Live's `TAddOnsHub` variant alternatives (`TConfigureRemoteSettings`, `TCheckInstalledAddOns` and so on).
  Request field names: `servicesUrl`, `resourceBaseUrl`, `licenseId`, `secret`,
  `addOnFilters`, `addOnId`, `backendId`, `cancel`.
- AddOns → Live:
  - `ReportEventIsDone {eventId}` (0x100135368)
  - `ReportAddOns {eventId, result, isDone}` (0x10014c858)
  - `ReportAddOnProgress {eventId, addOnId, finished, total, progress}` (0x10014d64c)
  - `ReportDeleteAddOnResult` and `ReportExtensionInstallResult`, each
    `{eventId, success, error}` (0x100135840, 0x1001360a0)
- **Inferred:** payloads are JSON objects. They are built as rapidjson object
  values (type tag 3) with a 64 KiB pool allocator, and the binary contains
  rapidjson's parse-error strings.
- Lifecycle: AddOns exits on `Shutdown request from Live` (0x100143f58) or
  `Shutdown since inactive` (0x100136324). It reports when it has been orphaned.
- Credentials: `SetRemoteSettings` carries a license ID and a secret. AddOns
  logs the license ID but masks the secret as `***` (0x100133828). No credential
  value was found in the files.

## Web Connector

**Launch and configuration.** Observed:

- `ableton_ping.main` reads `sys.argv[1]` as JSON. It configures logging
  (`logging.file_path`, `log_level`). A log above 1,000,000 bytes is renamed
  to `.old`, and its tail is copied into the new log. It opens a usage reporter
  at `aip_usage_data_dir/usage_report_prefix + ".webconnector"`, then calls
  `abl.webconnector.main.main(config, AbletonWebConnector)`.
- The native `AbletonWebConnector` module provides `HasInternetConnection`
  (`SCNetworkCheckReachabilityByName("services.ableton.com")`, reachable and not
  connection-required; 0x10083c584) and `IsCurrentProcessOrphan`.
- Config keys read by Python: `ipc_channel_id`, `wait_for_confirmation`,
  `app_base_path`, `app_exe_path`, `autoupdates_dir_base_path`,
  `aip_usage_data_dir`, `usage_report_prefix`, `services_endpoint`,
  `session_id`, `directory_connection`, `live_variant`, `platform`,
  `architecture`, `version`, `crash_detection_file`, `swapper_exe`,
  `swapper_sentinel_file`, `pid`, `skip_vcredist_update`, `commands` and
  `logging`.
- The same names, plus `wordsize`, sit together in Live's string block that
  starts at `web_connector_args_` (arm64 +0x5b1b740). Nearby are
  `ableton_ping.pyc`, `wc.log`, `upload_event_logs`, `check_for_auto_updates`
  and `no_sufficient_space_for_auto_update` / "Too little disk space for
  potential Live update".
- **Inferred:** Live writes this JSON file ("Exception when creating json file:")
  and decides which `commands` to send.
- Unknown: whether `session_id`, `version` and `architecture` come from the same
  writer, and what values Live sends.

**Flows** (Observed, `main.pyc:main`):

1. Use `DirectoryConnector(base=directory_connection)` when that key is present.
   Otherwise use `RPCConnector(endpoint_prefix=services_endpoint, session_id)`.
   With no reachability and no directory connection, log
   `no_internet_connection` and exit.
2. Always clean up old event logs.
3. If `upload_event_logs` is in `commands`, upload usage and crash logs.
4. If `check_for_auto_updates` is in `commands` and a leftover `<app>.Old` can be
   deleted, check, download and prepare, then install (see below).
5. If `skip_version` is in `commands`, mark the version as skipped in `info.json`.

Not observed in the Python: account login, authorization, Pack or content
download, or any browser flow. The native binary contains authorization and
website-link strings (`account/request-unlocks`, `authorize`, `reauthorize`,
`authorize_free_license`, `livepacks`, `checkforupdate`,
`Ableton-Challenge-Response-Token`, `Unlock/Unlock.json`). They are referenced
only from shared-library functions (0x10072c13c–0x10072df58, 0x1008476a0). No
path from `entry` to them was established. **Inferred:** they are linked-in
shared code, and Live itself owns authorization and Pack download (Live has
`FetchDownloadablePackListFromWeb` and `Unpack Tool: Unpacking `).

**Usage data.** Observed in `reporting.pyc`:

- Each event line is a UTC timestamp `%Y-%m-%dT%H:%M:%S` plus `.%06i=`, the
  event name, then an optional space and JSON.
- Log families carry the suffixes `.webconnector`, `.indexer`, `.crashlog`,
  `.swapper` and `.push2`. A file is locked through `.log.lock` and renamed
  `.log+processed` after upload.
- Uploads go through XML-RPC `reports.upload_event_log(frame, Binary)` and
  `reports.upload_log(frame, run_id, kind, Binary)`.
- The 24 `EventTypes` (`start` … `cleanup_event_logs`) are listed in the
  bytecode.

## Application update mechanism

Observed in bytecode unless marked otherwise.

1. **Check.** Tags are `win64`, or `mac-intel`/`mac-<architecture>`, plus a
   variant tag from `VARIANT2TAG` (Suite/Standard/Lite/Intro/Trial/Beta →
   lower case). `check_for_auto_updates` returns at most one target version with
   a list of deltas `{name, checksum, version}`. More than one version raises an
   assertion. Leftover `_autoupdates/pending_update` is cleaned first.
   - The directory connector instead reads `<dir>/from/<from>/to/<to>/*.asu`
     (layout from `README.org`). It matches tags to file-name tokens
     `mac_intel`, `mac_universal`, `mac_arm`, `win_64` and the variant names.
2. **Confirm.** Send `update_available <version>`. When confirmation is
   required, wait for `continue` or `cancel`.
3. **Download.** For each delta, write `<dest>.part`, compute MD5 while reading,
   compare with `checksum` (`WrongChecksum` on mismatch), then rename. State is
   kept in `<autoupdates_dir_base_path>/_autoupdates/info.json` as
   `versions[v].status` ∈ {`downloading`, `available`, `prepared`, `skipped`},
   with `prepared_version`. Deltas go in `_autoupdates/deltas/`. The integrity
   check is MD5 only; no signature verification of `.asu` files was observed.
4. **Prepare.** Copy the installation with `shutil.copytree(symlinks=True)` to
   a sibling `.<Name>_updated.app` (`connector.pyc:create_copy_app_base_path`).
   Abort if the file counts differ. Then unpack each `.asu`:
   - An `.asu` is a ZIP file whose top-level directories are `created/`,
     `updated/` and `deleted/`.
   - The Unix mode is taken from `external_attr >> 16`. A symlink entry stores
     its target as the entry content.
   - A file `updated/…/X.xdelta` is rebuilt as `xdelta3 -d -s <app>/…/X <delta> <new>`.
     `delta_creator.pyc`/`diffing.pyc` produce xdelta only for `.alp` files
     (`ALPDiffer`); other changed files are stored whole after an MD5 comparison.
   - Apply order: delete the `deleted/` paths, move in `created/` (an existing
     file is renamed `.orig`), then replace from `updated/`.
   - On Windows, `updated/Redist/vcredist.exe` is also run.
   - Live's bundle contains three `.alp` files (`GUI.alp`, `Graphics.alp`,
     `Languages.alp`). Their format is not ZIP and was not decoded.
5. **Apply.** Send `update_ready_to_apply`. Poll `IsCurrentProcessOrphan` once
   per second; it becomes true when Live exits. Refuse when `crash_detection_file`
   exists or when `ps -x` shows another process with `app_exe_path`. Then copy
   the Swapper and every `.dylib` next to it and in `<app>/Contents/Libraries`
   into a fresh temp directory, and run it from there.
6. **Swap** (Swapper):
   - Requires `live` and `copy`, which must exist and share a parent directory
     (0x10013245c, 0x100133100).
   - Waits for its parent process to finish unless `--nowait`, polling with `sleep(100)`
     (unit inferred to be ms; 0x100131d48). Aborts with code 3 if Live is running (0x100138a10).
   - Renames `<live>` → `<live>.Old`, then `<copy>` → `<live>`. If the second
     rename fails it renames back (`rollback_rename_1`). It then deletes
     `.Old` and touches the sentinel file (0x100134da4).
   - It records `pid`, `parent_pid`, `commit_id`, `start`/`end`, rename and
     delete events in the `--usagedata` file. The Web Connector later uploads
     that file as the `.swapper` family.
   - On the next run, the Web Connector deletes any remaining `<app>.Old` before
     checking again.

## Add-ons

Observed:

- **Remote list.** `get_addons` returns a list. Each download record decodes
  `domain`, `platform` (`*` or `mac/universal`), `version`, `min_live_version`,
  `is_required`, `name`, `info`, `download_url`, `info_url` and `download_size`
  (0x1001314d4). No checksum or signature field is decoded. The integrity check
  for downloaded add-ons is **unknown**; nothing beyond the size field was seen.
- **Extensions backend.**
  - Storage: `<root>/Extensions`, `<root>/Extensions Data` and
    `<root>/Ableton Extensions` (0x10014f3a4, 0x1001c6f48, 0x1001c702c). The
    roots come from virtual path-provider calls and are unknown.
  - Installation (`InstallFileForBackend`, 0x10013a100) opens a ZIP archive and
    reads its `manifest.json`. The manifest needs string fields `author`,
    `entry`, `name` and `version`, plus `minimumApiVersion`; `displayName` is
    also read, and whether it is required is unknown (0x100156c38).
  - An archive entry that would resolve outside the target is rejected with
    "Archive contains unsafe path" (0x1001501e8). An existing target directory
    is an error.
  - Delete moves the extension to the Trash and removes the directory if that
    fails (0x100139cf4).
  - The UTF-16 MIME types `application/vnd.ableton.extensions` and
    `application/vnd.ableton.splice:splice` appear in Live (`strings -el`) and in
    the Web Connector (0x100ef4914, 0x100ef48c8).
- **Splice backend.** The bundle ships
  `Misc/Splice/SpliceAbletonLive_1.1.0_e0c725d.zip`: 80 entries, a
  `SpliceAbletonLive.vst3` bundle with a JS front end (`splice-zip-listing.tsv`).
  AddOns can check for a newer version and download it to a temporary file with
  `splice-download-info.json`. Partial downloads are resumed or discarded.
- **Packs.** No `.alp` or Pack handling was found in AddOns.
  `Misc/example_packs.json` (31 records: `pack_unique_id` such as
  `www.ableton.com/227`, `title`, `url`, `revision`, `download_size`,
  `installation_size`, `requires_mfl`, `teaser`) belongs to Live. Pack
  download, verification and installation are Live-main questions.

## Reimplementation scope

**Proposed** classification. It is not a decision.

| Behavior | Classification |
| --- | --- |
| Out-of-process helpers with crash isolation, orphan detection and inactivity shutdown; a local IPC channel with named events | Needed as a design pattern only. Wire compatibility with Ableton's helpers is not needed |
| Atomic application replacement: prepare a sibling copy, wait for exit, rename with rollback, clean `.Old` on next start, refuse while the app runs or after a crash marker | Needed if the candidate ships self-update (FEAT-DELIVERY). The rename/rollback contract can be specified from this page |
| Delta package format (`.asu` ZIP, `created/updated/deleted`, VCDIFF for large archives, MD5 per delta) | Optional. MD5-only integrity is below a reasonable bar; a candidate should use signed packages |
| Extension package install (ZIP + `manifest.json` schema, path-traversal rejection, trash on delete) | Needed if FEAT-ECOSYSTEM includes an extension format. Fields are known; semantics of `entry`/`minimumApiVersion` are unknown |
| services.ableton.com XML-RPC (`software`, `reports`, `get_addons`), usage-data upload, Splice distribution, license/secret relay, www.ableton.com links | Ableton-service-specific, out of scope |
| Pack list, download, `.alp` unpacking and installation; authorization | Live main, not these helpers. Needs the Live project |

## Unknowns and questions for the main Live project

- How Live builds the WC config and the AddOns `--cid` value, and when it starts
  each helper. This covers the `auto_updates_enabled` preference, the free-space
  gate and the `commands` selection, starting from `StartWebConnector` and
  `AddOns: start process` (Live arm64 +0x5aafa02, +0x5bd3bc7).
- What Live does on `update_available`, `update_ready_to_apply` and
  `update_failed` (UI and confirmation), and how it uses the sentinel file.
- IPC wire framing, socket type and which side binds.
- Remote request and response shapes for `get_addons` and
  `check_for_auto_updates`, and the delta host.
- Extension API semantics (`entry`, `minimumApiVersion`) and the path roots.
- Pack download and `.alp` format and installation; authorization flow.
- Runtime confirmation of any of the above (Phase 4).
