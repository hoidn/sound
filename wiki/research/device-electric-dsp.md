# Electric audio by extracted execution (T1.2)

**Question.** What audio does the bundled Electric instrument produce for note events and stored
parameter values, observed by running its own x86_64 code? Which parts are deterministic, how do
the mallet, fork, damper and pickup controls act, how many voices does Polyphony allow, and what
comparison metric can a device spec state?

**Answer (X, draft).**

- **Rendering.** The [Corpus harness](device-dsp-extracted.md#harness) renders Electric with no
  new bindings. Renders are bit-for-bit repeatable for these variations:
  - host blocks of 64, 256, 333, 512 and 2,048 frames;
  - flush-to-zero and denormals-are-zero;
  - transport playing at 90 BPM;
  - any input buffer content and input flag.
- **Randomness.** Every note carries a random component. Its generator is seeded from the clock
  once per instance, so it is not reproducible in Live. At the defaults it lies about 42 dB
  below the note. The damper controls set most of it.
- **Timing.** Notes are placed on a 1 ms control grid. The rule is exact for 318 note-ons and 201
  note-offs. The sound starts one control period after the grid point; a release starts at the
  grid point.
- **Voices.** Polyphony index p allows p + 2 voices, for all 31 values. This settles the meaning of
  the labels `2` … `32`. A voice is stolen as follows: released voices go first, then the oldest
  held one, and the stolen voice fades out linearly over one control period.
- **Laws.** Exact laws were found for Volume, PickupAmpOut, PickupAmpKeyboardScaling and the
  tuning controls. The other controls are described by measured effects at five values each, plus
  retained reference renders.
- **Parameter changes.** Most parameters are read at note-on or note-off, so a change does not
  affect a sounding note. Volume ramps linearly over 4,000 frames. MalletForceVelocity ramps over
  about 0.1 s, and its start-up ramp makes notes in the first 0.1 s after creation louder.
- **Metric.** One-ulp libm changes move the pitch by about two thirds of a binary32 ulp bound.
  The arm64 slice has 171 fused multiply-adds; the x86_64 slice has none. A waveform metric is
  therefore unusable. Per-case tolerances come from four reseeded and two libm-perturbed variants.

Evidence: [t12-electric-v1](../../analysis/ableton-live-12.4.3/r2/t12-electric-v1/manifest.json),
regenerated by `sh run.sh` (about 40 s on 8 cores). It holds:

- `harness/`: the loader copy;
- `el.py`: protocol, host values, presets;
- `measure.py`: the metric;
- `run_cases.py`: 120 reference renders with measures and tolerances, in `results/cases.json`;
- `probes_events.py` and `probes_params.py`: timing, voices, tuning, parameter timing, gain laws and
  protocol, in `results/probes_*.json`;
- `raw/<case>.wav` and `raw/<case>.script`: the retained renders, mono binary32, about 14 MB;
- `results/fma_scan.txt`.

The behavioral contract is [SPEC-DEVICE-ELECTRIC](../specs/device-electric.md).

Like Corpus, the engine builds its module graph from an embedded text patch. The patch names
modules for the keyboard, mallet, noise damper, fork, pickup, mix, volume and stereo, plus a
Scala tuning table. Only behavior observed in renders is stated below. The patch text is cited
here as context, not as behavior.

## Render protocol

`el.py`, used for every case:

1. Create the instance and set the sample rate.
2. Send the 33 host values in index order. These are the stored values converted as
   [N5](device-parameter-mapping-native.md#electric-loungelizard-complete-33-indices) traces it:
   - 0..1 values are passed unchanged as binary32;
   - Polyphony and PickupModel are passed as their index;
   - KeyboardTranspose is rounded to 1/32768 and then truncated;
   - index 32 is always 48.
3. Process a warm-up with no events: 11,264 frames at 44.1 kHz, 12,288 at 48 kHz. The warm-up is
   discarded; it is asserted to be exactly zero.
4. Deliver the events at frames counted from the end of the warm-up, in blocks of 512, with input
   flag 0 and transport {0, 0, 120}.

The warm-up is a whole number of blocks and of 1 ms control periods. Render frame 0 is therefore
a block start and a grid point. The warm-up also exceeds the start-up ramp (below), which matches
ADR 0004's settled start. Both channels are bit-identical in every render, so renders are kept
mono.

The stored defaults are the constructor values (SPEC-BUNDLED-DEVICE-PARAMETERS "Default when
absent"). Volume is the constructor's binary32 `0x3f346d11` = 0.7047892213; N5's table prints it
rounded to 0.704789. The 17 shipped Electric presets and the Defaults preset are read from their
`Manual` values.

## Determinism and protocol

`results/probes_params.json` `protocol`:

| Check | Result |
| --- | --- |
| Re-run in a new process | Bit-identical |
| Host blocks of 64, 256, 333, 2,048 frames against 512 | Bit-identical; note at a grid point |
| MXCSR flush-to-zero and denormals-are-zero | Bit-identical |
| Transport playing, position 16, 90 BPM | Bit-identical |
| A 440 Hz sine in the input buffers, input flag 0 or 1 | Bit-identical to silent input |
| N5 reset sequence (ResetA, then index 0 again) or ResetA alone, after the warm-up | Not bit-identical. Envelope within 0.0009 dB, partial amplitudes within 0.009 dB |
| Rate 44.1 kHz, warm-up, then 48 kHz, against 48 kHz directly | Not bit-identical. Envelope within 0.0009 dB, frequencies within 0.01 ulp bound |

**Random component (X).** `srand(time(0))` runs once, at instance creation. The default C4 render
then calls `rand` 34,272 times, about once per frame while a voice sounds, plus once per block.
Renders with other clock values differ from the first sounding frame on.

The level of the difference is 20 log₁₀ RMS((x_a − x_b)/√2)/RMS(x_a) over the note. It is
−41.6 dB at the defaults (range −43.2 to −38.6 over four seeds about 37 days apart) and −25 dB
with DamperAmount 1. DamperBalance 1 leaves −76 dB during the note and moves the noise to the
release. Across the cases the mean ranges from −76 to −3 dB; the −3 dB case is MalletStiffness 0,
where the deterministic part is almost silent.

Consecutive small seeds give correlated first outputs, so the probes use seeds far apart.
Inferred: in Live the noise differs between instances and sessions. No render can fix its
waveform.

**Activity flag.** `CalcA` reports 1 for 262 blocks after creation, without a note, and then 0.
After a note released at frame 4,096 it reports 1 for 293 blocks, about 3.4 s, and then 0.
How Live uses the flag is unknown. Live might stop calling `CalcA` while the flag is 0. The grid
phase would then depend on that history.

**Start-up.** Without the warm-up, a note at frame 0 sounds 14.9 dB louder than a settled note.
Notes from frame 4,400 on match the settled level (`start_up_note_level_db_by_onset_from_creation`).
With index 9 left unsent, a note at frame 0 is within 0.66 dB of a settled note
(`laws.start_up_index9_unsent_early_vs_late_db`). Almost all of the start-up effect is therefore
MalletForceVelocity, which ramps from the built-in patch value to the sent value (see
[parameter timing](#parameter-timing)).

## Events and voices

`results/probes_events.json`.

**Event timing (X, exact for all tested events).** Let P = ⌊fs/1000⌋, which is 44 frames at
44.1 kHz and 48 at 48 kHz. Frames count from the instance's first processed frame. For an event
at frame f:

- let g be the start of the control period that contains f;
- if g lies before the start of f's host block, g' = g + P; otherwise g' = g.

Then:

- after a note-on, every frame before g' + P is exactly 0. The first non-zero frame is g' + P in
  318 of 318 note-ons: blocks of 512, 64 and 333 at 44.1 kHz, and 512 at 48 kHz;
- a note-off changes the output from frame g' on (201 of 201: 44.1 kHz with blocks of 512 and
  333, and 48 kHz).

This is Analog's grid ([device DSP](device-dsp-extracted.md#analog-results)), with the sound
starting one period later. In 118 of the 119 sounding reference cases the first non-zero frame
is exactly g' + P. In E-Piano MKII Hollow it is g' + P + 2, because the attack rises from below the binary32
resolution.

**Note messages (X).**

- A note-on with velocity 0 renders bit-identically to a note-off.
- Release velocity 127 renders bit-identically to 0.
- Channels 2 and 16 render bit-identically to channel 1.
- A note-off for another key leaves the note unchanged.
- Notes 0 and 127 sound.
- CC64 at 127 holds released notes, at −20.4 dB 0.2 s after the note-off against −72.7 dB without
  it. Releasing the pedal releases them.
- Pitch bend shifts by ±12·r semitones, where r is the PitchBendRange host value. Bend at
  +8191 gives 523.237 Hz at r = 0.25, 622.29 Hz at 0.5 and 880.66 Hz at 1, from A4 at 440.33 Hz.
  r = 0 gives no bend.

**Voices (X).** In each test, n staggered held notes were rendered with and without the first
note, and the residual measured 0.1 s after the last note-on. DamperAmount was 0 to lower the
noise floor.

- For every Polyphony index p from 0 to 30, with n = p + 2 the residual is −16.0 to −3.5 dB:
  the first note still sounds. With n = p + 3 it is −61.0 to −57.3 dB, the noise floor: the
  first note was stolen. The voice limit is p + 2, so the labels `2` … `32` are voice counts.
- Three voices, notes 72, 67, 64, 60 in that order: dropping 72, the oldest, gives −62.1 dB; the
  others give −2.4 to −4.7 dB. The oldest note is stolen, not the lowest.
- Two voices: 60 held, 64 played and released, then 67. The released 64 is stolen (−59.9 dB); the
  held 60 is kept (−2.9 dB).
- A repeated key takes a new voice. Two strikes of 60 equal the sum of two single strikes within
  −64 dB, with 2 or 32 voices. One note-off releases both strikes; 0.2 s later the level is
  −105.5 dB.
- Stealing: the stolen voice's contribution is scaled by about 1 − (k + 1)/P for k = 0 … P − 1
  frames after the grid point g' of the stealing note-on, and is absent after that (−61 dB).
- Changing Polyphony while a note sounds changes the output from the next grid point g'. The
  note then falls away: −43.1 dB against −18.1 dB unchanged, for both 0 and 29.

- At the defaults, A4 is 440.329 Hz and C4 261.621 Hz. From note 48 up, the deviation from
  equal temperament repeats by pitch class, in cents:

  | C | C♯ | D | D♯ | E | F | F♯ | G | G♯ | A | A♯ | B |
  | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
  | −0.04 | −0.04 | 0.03 | 0.16 | 0.35 | 0.61 | 0.86 | 1.10 | 1.27 | 1.29 | 1.12 | 0.70 |

  Notes 60 to 108 lie within 0.06 cents of these values, and notes 48 to 59 within 0.23 cents.
  Notes 21 to 47 lie between −1.8 and +2.8 cents. Below note 21 the estimate is unreliable:
  the fundamentals are weak, and the binary32 ulp bound is about 10 cents near A0.
  `defaults_44` lists every note.
- 48 kHz agrees with 44.1 kHz within 0.12 cents from note 57 up. It differs by 4.7 cents at A0,
  which is one ulp bound there.
- KeyboardFineTune shifts every note by (v − 0.5)·100 cents: −49.6, −24.8, +25.0 and +50.0 at
  0, 0.25, 0.75 and 1 for C4. C6 is within 0.03 cents of these values and C2 within 0.8 cents.
- KeyboardTranspose t shifts by t − 12 semitones. The pitch-class pattern follows the sounding
  note.
- KeyboardStretch shifts every note by about the same amount relative to the defaults: +6.96 to
  +7.52 cents at 0, +3.55 to +3.77 at 0.25, −3.15 to −3.64 at 0.75 and −6.75 to −7.23 at 1, for
  notes 39 to 105 (`cents_re_defaults`). That is about (0.5 − v)·14.4 cents. No stretch that grows
  with distance from a reference note was found.
- Harmonics follow the fundamental exactly, because the pickup forms them from the fundamental.
  The libm variants move them in proportion.

## Parameter laws and section behavior

Host values v in 0..1 map to a controller c = 128v for v ≤ 0.5 and c = 126v + 1 above it, with
n = 0.5 at c = 64 and n = c/127 otherwise. This is Corpus rule U. The following laws are exact
(`results/probes_params.json` `gains` and `laws`); the sample ratios are constant within
2 × 10⁻⁶:

- **Volume:** output gain ∝ n(v)². v = 1 is +6.02 dB re the default, v = 0.5 is −12.04 dB re
  v = 1, and v = 0 is silent. The ratios match n² within 1.5 × 10⁻⁷ relative at 23 values.
- **PickupAmpOut:** gain = 15(c − 64)/64 dB re v = 0.5, from −15 dB to +14.77 dB, linear in v on
  each half. v = 0 is silent. This holds within 3 × 10⁻⁶ dB at 17 values.
- **PickupAmpKeyboardScaling:** gain = 2^((n − 0.5)(note − 60)/4). At v = 0 it is +18.06 dB at
  note 36 and −27.09 dB at note 96. At 0.5 it has no effect.
- **Quantization:** PickupSymmetry and PickupDistance act in steps of ⌊c⌋; 0.25 and 0.2525
  render bit-identically. Eleven other controls tested are continuous.

Measured effects at C4, velocity 100, values 0, 0.25, 0.5, 0.75 and 1
(`results/probes_params.json` `sweeps`; h = harmonic levels at 30 ms, dB):

| --- | --- |

## Parameter timing

A host value is set between blocks; frames below are render frames
(`latch_during_note`, `change_before_next_note`, `ramps`). The change was at 8,192, so g' = 8,228.
The note-off was at 12,288, so its g' = 12,320.

| Effect on a sounding note | Indices |
| --- | --- |
| From g' (Volume, Polyphony), g' + 1 (PickupModel) or g' + P (KeyboardFineTune, KeyboardTranspose, KeyboardStretch) | 2, 0, 23, 3, 30, 31 |
| From the note-off's g' on (release-time values) | 10–14, 16–18, 20, 27–29 |
| None; read at the next note-on | 1, 4–9, 15, 19, 21, 22, 24–26, 32 |

- **Volume** ramps linearly from the old gain to the new one over exactly 4,000 frames from g',
  at both 44.1 and 48 kHz. The ratio at frame k is 1 + (target − 1)(k + 1)/4000.
- **MalletForceVelocity** ramps in about 98 control periods at both rates. Notes struck before
  then use an intermediate value: at 44.1 kHz, onsets from 4,312 frames after the change are
  settled, and at 48 kHz from 4,704. Every other read-at-note-on value is settled for a note
  512 frames after the change.
- A fine-tune change to 1.0 had retuned the note to within 0.002 Hz of 269.29 Hz by frame 8,300.
  The transition itself was not resolved.

## Floating point and metric

- **libm.** Every inexact libm result was moved one ulp up and down (`XDEV_LIBM_ULP`), and
  measured on the graded elements (`results/cases.json` `variant_max_deviation_on_graded`).
  - Harmonic frequencies moved by at most 0.78 ulp bounds of the fundamental,
    b(f0) = 3·2⁻²⁵/θ² + 2⁻²³ with θ = 2πf0/fs. The exception is PickupSymmetry 0 at 2.66, whose
    harmonic 1 lies near −83 dB.
  - Harmonic levels moved by a median of 0.002 dB, by 0.05 dB or less in 97 % of the variants,
    and by at most 0.31 dB.
  - Low notes are the most sensitive. At A0 the graded envelope frames moved by up to 1.43 dB,
    and frames near beating nulls by up to 5 dB; those frames exceed the cap and are not
    graded.
- **arm64.** The arm64 slice has 171 fused multiply-adds in 63 functions; the most is 21, in
  `0x2400c`. The x86_64 `__text` has no VEX instructions (`results/fma_scan.txt`). Inferred: arm64
  differs at the scale of the libm variants. This was not executed.
- **Consequence.** Waveform comparison fails between seeds, so it cannot be a metric. The spec
  grades these measures: onset, 10 ms envelope, third-octave bands in 4096-frame windows, and
  harmonic frequency, amplitude and decay by [demodulation](../../analysis/ableton-live-12.4.3/r2/t12-electric-v1/fit.py).
- **Graded elements.** An element is graded when it is loud and none of the six variants moves it
  by more than 1.5 dB (2 dB/s for decay).
- **Tolerances.** Each tolerance is twice the largest variant deviation over the graded elements,
  with a floor. Frequency is graded at 4·b(f0) for every harmonic.
- **Spread over the 120 cases.** Median tolerances are 0.22 dB for the envelope, 0.46 dB for the
  bands, 0.43 dB for amplitude and 0.15 dB/s for decay. The largest is 2.96 dB.
- **Noise-dominated cases.** Four cases leave most loud envelope frames ungraded, because their
  deterministic part lies under the random component: MalletStiffness 0,
  MalletStiffnessKeyboard 1 at notes 36 and 84, and most of A0's tail.
- **Random component.** Its level is graded against the four-seed mean within ±6 dB, where the
  four reference values span 6 dB or less: 94 of 119 sounding cases.

  `out/conversions.tsv` prints Volume's `sent_for_default` as `0.704789`. That converts to a

- N5 and H4 call index 31 KeyboardStretch. In renders it acts as a near-constant detune of +8.4
  to −5.9 cents, not as a stretch.

## Limits

- **What X shows.** X shows what the x86_64 code computes for the stated calls. It does not show
  that Live makes those calls. Live's side rests on N5's static reading. Unknown: the event frame
  base, block sizes, the grid phase relative to the song, whether Live stops processing when the
  flag is 0, and when it runs the reset sequence ([Q-025](../questions.md#q-025-device-host-protocol-and-device-audio-acceptance)).
- **Substitutions.** These are glibc libm, the inferred Park–Miller `rand`, a fixed `time`, the C
  locale and the libc++ shim. No stream extraction failed: every log shows `cxx-failbits 0`.
- **Coverage.**
  - The other controls are sampled at five values; renders are retained at 0 and 1. Values in
    between have no closed form, except for the stated laws.
  - Not run: MPE and per-note bend, controllers other than CC64, aftertouch, and 88.2 kHz and
    higher rates.
- **arm64** was not executed.
